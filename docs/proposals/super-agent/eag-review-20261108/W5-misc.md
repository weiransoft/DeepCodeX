### P1

**P1-1　`icp/evidence-collector.ts:114-123` — 测试输出证据 head-only 截断丢尾部真实失败（❌ 确证）**
- 成因：`collectTestOutput` 先按 `=== stdout ===\n${stdout}\n=== stderr ===\n${stderr}`（114，stdout 在前、stderr 在后）合并，再 `lines.slice(0, 1000)`（118）取**前** 1000 行，123 仅追加"仅显示前 1000 行"标识。
- 后果：stdout 超长或错误集中在 stderr 尾部时，真实失败错误被整段丢弃，`ComplianceEvidence.content`（128）只剩 stdout 头部；`ComplianceEngine`/G-7 门禁基于残缺证据判定，直接对应事故"输出 head-only 截断丢尾部错误或证据"。与 `assembly.ts:384 .slice(-2000)` 保尾做法相反，属未修复残留。
- 最小修复：改 `slice(-1000)` 保尾，或 stdout/stderr **分别**保尾后再合并；截断标识写明被丢弃的是哪一段；至少保证 stderr 完整进入 evidence。

**P1-2　`tcs/object-storage.ts:767-770` 与 `1145-1147` — get 失败被吞并当作"文件不存在"谎报删除成功（❌ 确证）**
- 成因：`delete()` 中 `const existing = await this.get(key).catch(() => null);`（767/1145）把 `get` 的任意异常（网络/认证/权限/超时）静默转成 `null`，随后 `if (existing === null) return { key, deletedAt, permanent: true }`（768-770/1146-1147）把 `null` 一律解释为"对象不存在，已永久删除"。S3 与 OSS 两个适配器同款。
- 后果：读取真失败时删除流程根本没执行，却返回 `permanent: true`（删除成功），把真失败说成通过；上层若据此推进发布/清理流程会留下未删除对象。
- 最小修复：区分 404（不存在）与其它异常；仅 404 走 `permanent:true`，其它异常向上抛或返回 `{ permanent:false, error }`；去掉无差别 `.catch(() => null)`。

**P1-3　`dynamic/eag-dynamic-suggester.ts:115-120 / 404-409 / 185` + `suggestion-auto.ts:256-278` + core `session.ts` — 逃生门重放「带失败状态」修复只按写入方覆盖、消费方不强制（❌ 结构性确证，经 review-boundary 跨组核对）**
- 成因（本组）：触发层 `confirm_previous`（用户「执行这个」）与 `previousSuggestion`（185）不带失败状态；知情重试守卫 `acknowledgeFailedGoal` + `autonomousGoalRuns`（100-112/186-191，类型仅 `{goal, finalStatus, endedAt}`，不含 abortReason/failedTestIds）只挂 `execute_command` 路径，且仅在 :5431 注入 suggester 作 LLM 决策提示、消费时不参与。组装层 `buildAutoExecuteCommand` 把上轮失败诊断拼进 `--goal` 依赖**可选** `failureContext`，注释 258 明确「无值时输出与修复前逐字一致（零回归）」。

- 后果：4 条通道可重现「用户执行这个 → 裸重放不带失败原因」：① suggest_*/降级快照被消费 → :5686 第三参 undefined → 逐字零回归裸重放；② 即便走 notifyFailedGoalBlocked，`buildGoalBlockedDiagnostics`:1553-1556 在 abortReason+failedTestIds 同时为空时返回无 failureContext → :5962 不写字段（:5936-5937 doc 自认「重放命令与修复前逐字一致」），与 session.ts:7914 异常路径叠加；③ 知情重试 :5601 两参；④ Web 拦截路径（session-pool.ts:1433/:1440 只推硬编码泛化文案，全 packages/web 零命中 failureContext 相关字符串，⚠️ 最终回 core 后由 LLM 重新决策需运行时复核，未臆断）。新一轮 run 拿不到上轮失败状态，可能再次撞同一确定性失败并触发熔断 abort。

- 最小修复：`buildAutoExecuteCommand` 的 `failureContext` 改必填或由消费方强制注入（缺省时拒绝自动重放而非静默裸跑）；`consumeConfirmPreviousDecision` 增加「第三参非空」断言并统一做跨 run 失败判定（不只在 execute_command 路径）；3 处裸 `.set` 写入方统一补齐诊断。
