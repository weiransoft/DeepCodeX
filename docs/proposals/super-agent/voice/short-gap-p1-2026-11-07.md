- ⛔ **P1 与 P0 一样默认关，本轮仍不建议默认打开**：短句停顿确实变短

## 1. 根因再定位：伺服倍率被钳在 1.65

上一轮调研把 `num:xs` 归因为「0.900s 句内静音」，并做了离线裁剪模拟
（压到 0.3s → 4.064 u/s / 17.40%）。本轮直接看服务端日志与真机两段耗时，
发现还有更关键的一层：

```
[voice] 流式语速伺服 1段 倍率 1.65 目标 4.92字/秒
[voice] tts-stream 21字 ... chunks=8 ... audio=171KB
```

| 量 | 值 | 说明 |
|---|---:|---|
| 等效发音单元 | 14.30 | `首块 192 毫秒，整块 1821 毫秒。` |
| 最终输出时长 | 3.6589s | 3.908 u/s，偏差 20.57% |
| 输出内静音 | 0.900s（360/380/80/80ms） | `compress_internal_gaps()` 只压 >0.9s 单段，没命中 |
| 伺服倍率 | **1.65（钳位）** | `TTS_RATE_SPEED_MAX=1.65` |
| 反推伺服前时长 | ≈6.04s | 3.6589 × 1.65；原始静音 ≈1.485s，WSOLA 等比缩放后才是 0.900s |
| 若伺服想达标所需倍率 | ≈2.08 | 4.92 × 6.04 / 14.30，超过上限 |

所以伺服**自己修不了**：把 0.9s 静音压掉，段变短 → 所需倍率下降 → 才能
真正把语速拉回 4.92。`code:m` 在 atomic 下那块 3.396 u/s 是同一类现象
（54 字请求被服务端二次切分，短段带 0.959s 静音）。

**实现要点**：压缩放在 `compress_segment_gaps()` 里、在 `segment_servo_speed()`
与 `StreamingWsola` **之前**。若放到变速之后，必须先攒齐整段才能裁静音，
流式就没法边生成边吐，TTFA 会退化成整块模式。

## 3. 开关契约

| 位置 | 开关 | 默认 | 作用 | 回退 |
|---|---|---|---|---|
| 服务端 | `DCX_VOICE_SHORT_GAP=1` + 重启 | **关** | ≤20 单元段，>0.30s 句内静音压到 0.30s | 去掉变量重启；`/health.versions.shortGap` 回显 |

- 请求级解析与 `text_normalize.request_tns_enabled()` 同语义：
  `"0"/"false"/"off"/"no"` 视为关，避免字符串真值陷阱。
- **生产态只需服务端变量**：网关 `voice-api.ts` 会重建请求体、不透传额外字段，
  所以 `shortGap` 请求字段只在直连探针里用于 A/B，不能当 WebView 生效依据。
- 规则叠加顺序：既有「>0.9s 异常空白 → 0.45s」先跑，再对短块跑 0.30s 上限；
  >20 单元长块完全不受第二层影响（正常句读实测最长 0.68s）。
- 关闭态与改动前逐样本一致：`test_short_gap.py` 对 5 类合成波形 × 2 种单元数
  × 显式关/缺省关，共 20 组做 `np.array_equal` 比对。

## 5. 真机 A/B（8791 / sinan / speed 1.2 / tns-1.0）

### 5.1 单一权威口径

同一 sidecar、同一预热模型、同一语料与阈值；请求级 `shortGap` 让 off/on
在**同一进程内**交替采集，避免重启带来的权重重载与时段漂移。
`--atomic` 只替换探针里的「前端复刻切分」，服务端 `DCX_VOICE_ATOMIC_CHUNK`
另用一次重启做两态对照。产物 `/tmp/dcx-p1-ab/` 与 `/tmp/dcx-p1-ab-srvatomic/`。

### 5.3 补测 P0 服务端层（重启为 `DCX_VOICE_ATOMIC_CHUNK=1`）

上一轮 P0 报告把服务端那层写成「可选增强、不是收益来源、没有单独 A/B」。
本轮直接对照了同一段 54 字请求的 `split_long_text()` 结果：

```
atomic=False: '的 body 是 text，engine，voic' | 'e，speed，别漏 Bearer token。'
atomic=True : '的 body 是 text，engine，voice，' | 'speed，别漏 Bearer token。'
```

服务端关着时，前端 atomic 刚保住的 `voice` 又被服务端二次切碎。打开后：

| 格子 / 模式 | 服务端 atomic off | 服务端 atomic **on** |
|---|---:|---:|
| `code:m` atomic | 33.67% ❌ | **14.98%** ❌ |
| `code:m` atomic_shortgap | 27.04% ❌ | **10.87%** ❌ |
| `code:xl` atomic | 6.84% ✅ | 6.83% ✅ |
| `code:xl` atomic_shortgap | 2.10% ✅ | **1.82%** ✅ |
| `num:xs` shortgap | 2.70% ✅ | 2.70% ✅ |

**结论：P0 的「服务端可选」判断需要修正**——只要前端放出 >48 字请求
（atomic 允许到 59 字），服务端那层就是必要的。

|---|---|---|

### 5.5 为什么 `code:m` 还差 2.87 个百分点

服务端 atomic + P0 + P1 全开时，`code:m` 的四块是：

```
#1 26字 12.9u 2.619s 4.937u/s 静音=160ms
#2 48字 25.8u 5.248s 4.913u/s 静音=260ms
#3 39字 29.1u 5.935s 4.910u/s 静音=500ms
#4 54字 16.5u 3.736s 4.416u/s 静音=140ms   ← 离群点
```

#4 是 54 字请求，服务端拆成 `8.79u` + `7.71u` 两段各自伺服；两段各自的
首尾 padding（保留 20ms 头 / 80ms 尾）与 60ms 段间静音都进了整块音频，
而矩阵分母仍按「一块 = 一次请求」的 16.5 单元算。这是 P0 允许 >48 字块的
结构性代价，不是静音压缩能消除的。上一轮试过的替代策略（不合并超长块）
又会造出 5.9 单元碎片、违反 `MIN_BLOCK_UNITS=10`，已回退、未采用。

## 8. 诚实边界

1. **默认全关，本轮不建议默认打开**。P1 单独是严格改善（无劣化格），但
   短句停顿变短；P0 仍有一格 `code:m` 不达标。两者都不越过「WebView 本人
   试听确认」这道门槛。
2. **本轮数据不是 WebView 端到端**：所有采集来自「Python 复刻前端切分 +
   直连 sidecar」。`stripForSpeech` 会剥掉裸 URL / Markdown 代码块，真实回复
   的朗读内容与矩阵纯文本语料不完全等价。
3. **请求级 `shortGap` 不会经网关透传**，它只是 A/B 工具；生产态必须靠
   `start.sh` 的环境变量，否则桌面端不生效。
4. **服务端 atomic 两态用重启对照**，不是同一进程内交替；语速类判据按音频
   时长算、模型固定 seed 确定性（跨会话 43.71% / 1.12% / 20.57% 精确复现），
   但 TTFA 类指标不可跨会话比较。
5. **TTFA 受并行负载污染**：真机采集与静态检查、构建并行时首块延迟会抬高，
   不能拿 TTFA 项数变化当方案效果；判据与阈值一个都没改。
6. **未修复的历史违规**：`plain` 首块/全局 TTFA P95、大写下划线标识符、
   跨段 F0、网关 `tns` 不透传，以及本轮仍未达标的 `code:m`。方案与代价见
   调研报告 §4/§7、P0 报告 §5.3/§5.5 与本报告 §5.5。
7. **F0 / 频谱质心只是音色代理**，不等于说话人验证；ASR 回听只证明没吞字，
   不证明停顿自然。
