## 🔴 阻断性问题

### B-01：「群组」被窄化为「单角色 dispatch」，多智能体协同闭环缺失

用户原话是「检查**智能体群组**实现是否完成集成和接线」。而方案 L0 全部在解决「一个任务派给一个角色」：

- L0-1 让 `/team dispatch` 能在 Web 跑通 → 仍是**单角色单轮**
- L0-2 让 35 个智能体能成为 dispatch 候选 → **候选变多，但还是一次派一个**

那么「群组」体现在哪里？方案里唯一涉及多角色的是 L2（不做）的 seam 化，而 core 里**已经有的**多角色协同能力（`WorkflowLoopController` 八阶段、`RalphLoopController` 自主迭代、`fan-out` 类拓扑）方案一个字没提。

**这是需求理解的硬伤。** 用户要的是「多个智能体协同干活」，方案交付的是「单个智能体被正确点名」。两者不是一回事。

**修法**：方案必须新增一节明确「群组协作」的范围与形态，至少回答：

1. 本期是否交付「一次任务 → 多角色分派 → 结果聚合」？
2. 如果交付，用 `WorkflowLoopController`（八阶段串行）还是 `fan-out-aggregate`（并行）？
3. 如果不交付，必须**显式写明原因**并给出下一期计划，不能让读者以为 `/team` 就是群组。

我的判断：**至少要把 `/team autonomous` 与 `/team full-lifecycle` 在 Web 打通并给出可见进度**，否则「群组」永远只是命令行里的一个词。

### B-02：没有任何一条验收标准是用户可感知的

21 条验收项（A1-A5 / B1-B4 / C1-C4 / D1-D4 / E1-E3）全部是「函数返回什么」「单测断言什么」「tsc 是否通过」。**没有一个场景描述用户会看到什么。**

对照用户视角应有的验收：

| 应有（缺失） | 现状 |
| --- | --- |
| 「我在 Web 输入框敲 `/`，能看到 team 命令列表」 | 无 |
| 「我点了某个专家，输入框出现可读的 chip」 | 无 |
| 「dispatch 跑起来时我能看到它在用哪个角色、做第几步」 | 无 |
| 「跑完我能看到它改了哪些文件」 | 无 |

**修法**：每个 L 层至少补 1 条「用户可见」验收，用「用户操作 → 屏幕变化」的句式写，而不是「函数返回 X」。

## 🟡 建议性改进

### S-01：Web 输入框缺 team 入口，用户不可能发现这个能力

本次已给 Composer 加了「+」能力菜单（模型 / 技能 / 智能体三页签，见 `Composer.tsx` 的 `openMenu` / `insertToken`）。但**菜单里没有 team/角色**。用户要在输入框手敲 `/team dispatch --task ...`——这不可能被普通用户发现。

建议把「+」菜单加第四页签「角色」或把 team 子命令并入「智能体」页签的二级分组，点击即插入完整命令模板（带占位符如 `--task "<在此输入任务>"`）。

### S-02：默认智能体与 team 角色没有打通

本次刚做完「用户可预置默认 agent」（`settings.json` 的 `agents.default`，经 `resolveSettingsSources` 注入 `defaultAgent`，在 `appendAgentIndexMessage` 末尾自动激活）。

但方案里没说：**用户设的默认智能体，能不能同时成为 `/team dispatch` 的默认角色？** 如果两者各管各的，用户会困惑「我设了默认，为什么 team 还是选了别人」。

建议：`dispatch --role` 未指定时，优先级为「默认智能体（若其已注册为角色）> matchRoles 结果 > 报错要求指定」。

### S-03：`/team list` 列出 40 个角色对用户毫无意义

L0-2 做完后 `/team list` 会从 5 条变成 40 条。用户看到 40 行纯文本清单，信息量为零。

建议：(a) 按 8 个业务类别分组；(b) 每类默认折叠；(c) 标注哪些是预置、哪些是用户自建（本次 `preset` / `group` 元数据已贯通，可直接用）。

### S-04：错误提示的产品化缺失

dispatch 失败时用户看到什么？方案没有定义。参考 dsh：错误必须告诉用户「哪一步失败、可以怎么办」。建议至少覆盖三种：角色匹配失败（→ 建议关键词）、工具被拒（→ 说明审批策略）、轮次耗尽（→ 建议拆任务）。

### S-05：与「模型切换需重启」的体验冲突没人管

本次刚做了「模型保存自动重启引擎」（指纹比对 + `engine_restarted` 提示）。如果一次 dispatch 途中用户切了模型触发重启，dispatch 会怎样？方案必须定义：**重启期间 dispatch 任务的处理语义**（中断？排队？失败并提示？）。这是真实的体验断点。

## 🟢 亮点

1. **G1 的问题描述非常准确**：「用户敲了命令被当普通文本投给 LLM，静默降级」——这是最容易被忽略、也最伤用户信任的一类缺陷（不是报错，而是看起来成功）。
2. **N1-N5 非目标清单**，产品视角看非常专业：明确写出「不做什么」比「做什么」更能防止项目失控。
3. **L0 优先**，把「错误状态」和「增强」分开，没有为了方案好看把 L1 塞进第一期。
4. **L1-3 事件日志的 G5「可审计」** 是真正有产品价值的一条——用户问「为什么选这个角色」时有据可答。
