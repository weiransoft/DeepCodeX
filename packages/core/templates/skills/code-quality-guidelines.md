# Code Quality Guidelines

补充 Karpathy 原则的工程实践指南，聚焦类型安全、错误处理、测试覆盖、日志规范。

## 类型安全

- **禁止 `any`**：使用 `unknown` + 类型守卫替代 `any`
- **边界校验**：函数入口校验参数类型与范围
- **可选字段**：使用 `?` 或 `undefined` 明确表达可选性
- **联合类型**：使用判别式联合（discriminated union）替代宽松类型

## 错误处理

- **禁止空 catch**：`catch` 块必须记录或处理错误
- **错误分类**：区分可重试错误与致命错误
- **错误传播**：内部错误向上传播时保留原始堆栈
- **边界处理**：仅在系统边界（用户输入/外部 API）校验，内部代码信任契约

## 测试覆盖

- **单元测试**：每个公共函数必须有对应测试
- **边界用例**：测试必须覆盖空值、极值、异常输入
- **集成测试**：模块间集成点必须有集成测试
- **禁止 mock**：测试禁止使用 mock/占位/简化（遵循项目规则）
- **测试目录**：单元测试放 `packages/core/src/tests/`，E2E 脚本放 `tests/scripts/`

## 日志规范

- **日志级别**：DEBUG/INFO/WARN/ERROR 四级
- **结构化日志**：使用 JSON 格式，含 timestamp/level/message/context
- **敏感信息**：日志禁止输出密码/Token/PII
- **错误日志**：必须含完整错误堆栈与上下文

## 注释规范（遵循项目规则）

- **语言**：中文注释，详细且符合 Rust/Java 代码规范
- **函数注释**：每个函数必须有注释说明用途、参数、返回值
- **关键逻辑**：复杂算法、业务规则必须有行内注释
- **TODO/FIXME**：必须有对应实现，不能只是注释

## 代码组织

- **单一职责**：一个函数/类只做一件事
- **依赖方向**：高层模块不依赖低层模块细节
- **配置外置**：硬编码值提取为配置
- **命名清晰**：变量名表达意图，禁止 `temp`/`data`/`info` 等模糊命名

## 与 Karpathy 原则的关系

| Karpathy 原则 | 本指南补充 |
|--------------|-----------|
| Think Before Coding | 类型安全前置思考 |
| Simplicity First | 错误处理最小化（不处理不可能场景） |
| Surgical Changes | 测试覆盖修改范围 |
| Goal-Driven | 测试用例作为成功标准 |
