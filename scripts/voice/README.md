# 司南的本机语音 sidecar（MLX / Apple Silicon）

让 Web 与桌面端能用**语音**跟司南对话：说一句 → 本机 ASR（Qwen3-ASR，
缺失时回落 Whisper）转文字 → 正常走对话 → 回复按句切分 → 本机 TTS 合成 →
浏览器边播边继续收。

全程本机推理，音频不出机器。

## 为什么是独立进程

模型跑在 Python（MLX 的音频生态都在 Python），UI 在 WebView。中间用回环 HTTP 划界：

- 模型崩溃不拖垮应用
- 可以单独重启与压测
- 浏览器版与桌面版走**同一条**链路，不为桌面单独开洞

## 快速开始

```bash
# 1) 装依赖（一次性，约几百 MB）
bash scripts/voice/setup.sh

# 2) 起服务（幂等：已在跑就跳过；等到真能接请求才返回）
bash scripts/voice/start.sh          # 等价于 npm run voice:start
bash scripts/voice/start.sh -f       # 前台运行，便于看日志

# 3) 自检：只检查依赖，不起服务
scripts/voice/.venv/bin/python scripts/voice/mlx_voice_server.py --selftest
```

启动后打开 Web 设置 → 司南 → 声音，点「检测」应看到 ASR/TTS 双绿。

首次合成会下载模型权重（10~30s），之后就只加载一次。

### 谁来启动它

**没有任何一方会自动拉起 sidecar**：桌面壳只管拉起 Node 引擎，引擎只是把
`/api/voice/*` 转发到回环地址。模型进程的生命周期是独立的——这是刻意的
（见上文「为什么是独立进程」），代价就是需要单独启动一次。

`start.sh` 把这件事收敛成一条命令：检查 venv → 带 `HF_ENDPOINT` 镜像 →
后台启动 → 轮询 `/health` 直到就绪。日志追加到 `~/.deepcode/logs/voice.log`。

已在运行时不重复启动：重复 bind 会以 `EADDRINUSE` 退出，看起来像启动失败，
实际是"已经好了"，这种误报最容易让人去 kill 一个健康的服务。

## 端点

| 方法 | 路径          | 作用                                                                                                                                     |
| ---- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| GET  | `/health`     | 依赖与就绪情况，**不加载模型**，秒回                                                                                                     |
| POST | `/tts`        | `{text, engine, voice, speed}` → `audio/wav`；**超过 48 字自动分段合成再拼接**                                                           |
| POST | `/tts/stream` | 同上 + `interval?` → **流式** `[4B 大端长度][独立 WAV]` × N；长文本自动分段、**逐段语速伺服**，段内一条有状态 WSOLA 时间轴（见下文专章） |
| POST | `/asr`        | 原始 WAV 字节 → `{text, durationMs, model, backend}`                                                                                     |
| POST | `/warmup`     | 探测依赖（启动时已自动后台预加载配置里的引擎）                                                                                           |

引擎侧不直接暴露这些端点，而是经 `packages/web/src/api/voice-api.ts` 代理：
前端只跟同源 `/api/voice/*` 说话，token 永不出进程。

## 每次合成为什么要显式传 `max_tokens`

`generate_custom_voice` / `generate_voice_design` 的 `max_tokens` 缺省不是"按文本算"，
而是回落到 checkpoint 里的 `max_new_tokens = 2048`——按 12.5 token/s 折算约
**164 秒音频**。

合成是持锁串行的（MLX 推理并发不安全），所以一次跑飞的生成会把后面排队的
请求全部堵住。前端的超时是 60s，表现就是：

```
语音服务不可用（http://127.0.0.1:8791）：This operation was aborted
```

sidecar 侧同时出现一串 `BrokenPipeError`（合成完了，客户端已经走了）。

现在 `max_tokens_for(text)` 按实测语速（4.1 字/秒）推上限并乘 1.5 余量：

| 文本长度 | token 上限   | 折算音频上限 |
| -------- | ------------ | ------------ |
| ≤ 66 字  | 200（下限）  | ~16s         |
| 120 字   | 548          | ~44s         |
| 160 字   | 731          | ~58s         |
| ≥ 336 字 | 1024（上限） | ~82s         |

实测（RTF≈0.20）：三块约 80 字的请求并发排队，最慢一块 **10.5s** 返回；
曾经卡死 180s 的重复文本现在 **4.4s** 完成。边界用例见
`test_max_tokens.py`（`python3 scripts/voice/test_max_tokens.py`）。

另外启动时会在后台线程预热配置里的引擎：冷加载实测 13s，不预热就落在用户
第一句上，叠上队列排队很容易啃掉 60s 预算。预热后首句合成约 **200ms**。

## 司南音色预设与语速（2026-11-06 重设）

配置的 `voice.voice` 现在写**预设名**，由 sidecar 的 `VOICE_PRESETS` 展开成
`(speaker, instruct)`。之所以不把两者拆成两个配置字段：前端 `/api/voice/tts`
只有一个 `voice` 值，而且音色底子与风格指令必须成对调整。

| 预设            | speaker  | 风格指令                                                                 |
| --------------- | -------- | ------------------------------------------------------------------------ |
| `sinan`（默认） | `serena` | 对齐 core 的「成熟女性、中低音区、克制不撒娇、句尾下沉」，语速改「稍快」 |
| `sinan-bright`  | `vivian` | 更亮、更利落的备选                                                       |

> **2026-11-08 第九轮补充**：`voice` 填自由描述（而不是上表的预设名或 9 个
> 预置 speaker 名）时，sidecar 默认把它归一到 `sinan`，不再把整段描述当
> `instruct`——中英混杂、含矛盾语速词的长描述实测会让长文本逐块漂移语速与
> 音色。详见后文「稳定音色身份」章节与 `DCX_VOICE_STABLE_IDENTITY` 回退开关。

同文本（41 字）实测：

| 组合                        | 语速           | F0 中位                        |
| --------------------------- | -------------- | ------------------------------ |
| `vivian` / speed 1.0        | 4.07 字/秒     | 237.6Hz                        |
| `sinan` / speed 1.0         | 4.10 字/秒     | **213.3Hz**（低 24Hz，更沉稳） |
| `sinan` / speed 1.2（默认） | **4.92 字/秒** | 222.2Hz                        |

**`speed` 用 WSOLA 保调变速，不是重采样。** 以前 `np.interp` 让音高跟着速度
一起变：speed=1.25 时 F0 237.6 → 279.1Hz（+17%），听感是磁带快进、像换了个人。
WSOLA 用波形相似重叠相加做时间伸缩，纯正弦上速度倍率误差 <1%、F0 完全不变；
真实语音上 F0 估计波动约 4%。边界用例见 `test_voice_preset.py`。

## 流式生成 `/tts/stream`

`generate_custom_voice(stream=True, streaming_interval=...)` 是**真增量**：每攒够
`interval × 12.5` 个声学 token 就用 `decoder.streaming_step` 解出一段音频。
sidecar 把每段独立封成 WAV，用 `[4B 大端长度][WAV]` 逐块 flush 下发；
网关 `/api/voice/tts/stream` 逐块 pipe，前端 `streamSpeech()` 按长度切分后
可逐块解码排进时间轴。

真机实测（41 字、热态、CustomVoice 1.7B）：

| 模式              | 首个音频可用 | 总生成耗时 | 音频总长 |
| ----------------- | ------------ | ---------- | -------- |
| 整块 `/tts`       | **1.90s**    | 1.90s      | 8.33s    |
| 流式 interval=1.0 | **0.394s**   | 1.93s      | 8.40s    |

即首字延迟降约 5 倍，**总耗时几乎不变**——流式只改善"多久开口"，不会让整段
生成变快。

绝对值会随 sidecar 负载波动（冷/热、连跑次数），所以又在**桌面端引擎网关上
做了同批严格对照**：两侧都显式传 `engine=qwen3-customvoice / voice=sinan /
speed=1.2`，返回字节数完全一致（整块 400034B、流式 403698B），确认音频等价：

| 路径                   | 整块首字节 | 流式首字节 | 网关额外开销 |
| ---------------------- | ---------- | ---------- | ------------ |
| 直连 sidecar           | 3539ms     | 368ms      | —            |
| 经 `/api/voice/*` 网关 | 3591ms     | **412ms**  | 44~52ms      |

这一批负载偏高，但**倍数稳定在约 8.7 倍**，且网关逐块 pipe 只多花几十毫秒，
没有把流式收益吃掉。

### 分块边界能不能直接拼

逐块实测（41 字 / interval 1.0）：11 块，每块 0.807s，合计
**8.399s ≈ 整块 8.333s**。也就是说流式块**不是带重叠的 OLA 片段，而是
同一段音频按时间切开**，块内的大段静音是模型本来就生成的语义停顿。

所以播放端用 `ScheduleOptions.continuous` 走另一套规则：**不裁静音、不加标点
停顿、不补 60ms 尾音**，直接 `start(when, 0, buffer.duration)` 接在上一块的采样
点上。裁静音会连停顿和字一起吞掉，加 gap 会让 11 块多出数百毫秒空转。整句音频
仍走原来的 `findSpeechBounds` + 停顿逻辑，两条路径互不干扰（S1 用例锁住）。

**但「能直接拼」的前提是变速不能在每块边界重启。** 修复前 `speed=1.2` 时
相邻块边界样本跳变中位 2.8% / 最大 19.4%，而 `speed=1.0` 只有 0.1% / 1.2%
—— 失真来自逐块独立 WSOLA，不是「分块」本身。解法见下一节。

### 跨 chunk 有状态 WSOLA（流式默认开，2026-11-06 第二轮）

`StreamingWsola` 把 `time_stretch_wsola()` 的帧状态搬成实例状态：输入缓冲、
理想分析位置 `ideal_xpos`、合成位置 `ypos`、搜索用的上一帧重叠区 `target`、
OLA 累加 `out`/`weight` 全部跨 `feed()` 延续。输出块只是这条轴的连续切片。

> **第三轮（语速伺服）之后的口径修正**：现在不再让「整个请求共用一条轴」，
> 而是**每段一条轴**——每段的倍率由该段实测语速决定，段内仍由同一个
> `StreamingWsola` 实例保证连续；段与段之间改用 60ms 微静音衔接。下面
> 「218ms 首字节」是第二轮的数据，第三轮的取舍见下一章。

关键约束：`feed()` 只在 `ideal_xpos + frame_len + search <= x.size` 时处理帧，
即**等搜索右窗完整可用**；`flush()` 才放宽到只剩一帧。否则先到的块 `hi` 会被
clamp，同一段音频「分块喂」和「整段一次喂」的帧序列就不同，结果会悄悄漂。
额外等待只有 `search = 256` 样本 ≈ 10.7ms @24kHz，不影响首字延迟。

因此有一条可验证的强保证（`scripts/voice/test_streaming_wsola.py`）：

```
分 N 次 feed() + flush()  ≡  整段一次 time_stretch_wsola()   （逐样本相等）
```

三种语速（1.2 / 0.85 / 1.5）、等长分块与不规则分块、含「不足一帧」的小块
全部逐样本相等；合成信号上块边界最大跳变从逐块独立变速的 **44.3% 降到 4.5%**
（剩下的是波形本身斜率与 PCM16 量化，不是变速重启）。

**真机复测**（同一 sidecar、41 字 / speed=1.2 / interval=1.0）：

| 指标                 | 逐块独立 WSOLA（修复前） | 有状态 WSOLA（修复后）                | speed=1.0 基线 |
| -------------------- | ------------------------ | ------------------------------------- | -------------- |
| 边界跳变 中位 / 最大 | 2.8% / 19.4%             | **0.3% / 2.5%**                       | 0.1% / 1.2%    |
| 流式拼接总时长       | 8.399s                   | **8.333s**                            | 10.000s        |
| 整块 `/tts` 时长     | 8.333s                   | 8.333s                                | 10.000s        |
| 长文本 164 字        | 50.45s / 21.69s 静音     | **33.366s / 0.67s 静音 / 4.92 字/秒** | —              |

流式拼接总时长与整块**完全相等**，就是「分块喂 == 整段一次变速」在真机上的
直接证据。网关严格同参对照（**第二轮数据**）：整块首字节 1891ms、流式
**218ms**（约 8.7×），网关额外开销 6ms；流式 12 块、结尾残留 0B、长度
异常=false，字节数比整块多 532B 正好是 12 个 WAV 头。第三轮为消除「模型按块
自选语速」改成段级伺服后，首块延迟变成「首段生成完」（见下一章的取舍说明）。

长文本仍有两处较大跳变（6.03% @16.32s、13.53% @24.66s）。定位后确认它们
**全部落在 41 字段接缝**：164 字被 `split_long_text` 切成 4×41 字，接缝约在
8.33 / 16.67 / 25.00 / 33.33s —— 是两次独立模型生成的硬拼接，不是变速重启；
整块 `/tts` 同样有这个接缝（见「已知限制」第 11、12 条）。单段 41 字的最大跳变
只有 2.5%，所以正常播报（前端块长已压到 48）不会遇到。

`flush()` 必须调用：最后 `frame_len + search` 个样本还压在 OLA 缓冲里，漏掉
每句末尾会被吃掉一小截（实测多出 1 个 0.024s 尾块）。`speed=1.0` 直接透传、
不引入任何缓冲延迟；总输入 <4096 样本时也与整块实现一致地原样返回，避免句尾
突然变速。

根因消除后**流式默认开**。设置页开关仍可手动关（回退整块 `/tts`）。存储键升到
`dcx.voice.streamPlayback.v2`：上一版可能留下显式 `"0"`，升级后第一次读取会
一次性删掉旧键并采用新默认；用户之后再手动关会写 v2 的 `"0"`，仍被尊重
（`packages/web/tests/voice-preference.test.ts` 的 P1~P8 锁住）。

### 播放队列已接入（2026-11-06）

`SpeechQueue` 现在是**双路径**：没注入 `streamSynth` 就走经过 599 条用例验证的
整块链路；注入了走新增的生产者-消费者分支（`drainStreaming()`）。第一片音频
到达就排程，不必等 `streamSynth` 的 promise resolve（S2 用例锁住"整块生成还没
结束就已出声"）。

- **开关**：设置 →「形象与声音」→「流式播报」，**默认开**（跨 chunk 有状态
  WSOLA 已消除变速边界失真，见上一节），存
  `localStorage["dcx.voice.streamPlayback.v2"]`（`"0"` 显式关闭）。关掉时
  `streamSynth` 返回 0 块，队列静默回退整块合成，不报错也不刷提示。
- **诚实降级**：流式请求失败或返回 0 块 → 该块转交整块 `/tts` 重试；只有整块
  也失败才回调错误。`AudioContext` 不可用时整条链路降级到元素播放，逐块播
  会有元素切换开销，但**一定出声**。
- **打断**：`stop()` 会 abort 掉响应流并递增 generation，迟到的 chunk 回收掉，
  不会串进新一轮时间轴（S5 用例锁住）。

边界用例：`packages/web/tests/voice-stream.test.ts`（S1~S5）。

## 长文本退化：为什么「前后两句语速不一样」「讲了几句就中断」

2026-11-06 真机反馈。先澄清：**播放链路没断**。sidecar 日志里那一轮有
`180字 → 69 chunks → 26s` 的流式请求；把音频拼回去量化后，发现里面塞了
**21.69s 连续静音**，折合语速从正常的 4.88 字/秒掉到 3.25 字/秒。

用整块 `/tts` 扫不同字数（`speed=1.2`），定位到 Qwen3-TTS 的**长文本生成塌缩**：

| 字数 | 时长   | 折合语速   | 最长连续静音 | 静音起点 |
| ---- | ------ | ---------- | ------------ | -------- |
| 14   | 3.00s  | 4.67 字/秒 | 1.10s        | 1.45s    |
| 41   | 8.33s  | 4.92 字/秒 | 0.66s        | 1.39s    |
| 55   | 16.75s | 3.28 字/秒 | 4.67s        | 12.08s   |
| 96   | 29.29s | 3.28 字/秒 | 21.49s       | 7.81s    |
| 164  | 50.04s | 3.28 字/秒 | 21.51s       | 28.53s   |

两个特征：退化后语速恒定 **3.28 ≈ 4.92 / 1.5**（正好是 `max_tokens` 的安全余量）；
静音起点 + 静音长度 ≈ 总时长，说明多出来的 token 全解成**尾部静音**。

**只裁尾不够。** 96 字那次裁掉尾音后只剩 8.00s 有声片段，而按正常语速应有
19.5s——模型在长文本中途就塌缩了，后面的字根本没念。所以真正的修复是
**别让长文本一次性进模型**，分四层落地：

1. **前端块长**：`player.ts` 把 `BLOCK_CHARS` 从 72 压到 40、`MAX_BLOCK_CHARS`
   从 160 压到 48；新增 `splitLongText()`，单句超长时优先在
   `。！？!?；;，,、：:` 处二次切分，拼回去逐字等于原文（B6/B7 用例锁住）。
2. **服务端兜底**：`TTS_MAX_TEXT_CHARS = 48` + `split_long_text()`。
   `/tts` 与 `/tts/stream` 都按同一套规则切；每段重新 `prepare_sampling(voice)`
   重置固定种子，避免跨段随机状态串味。变速方式在第三轮已改为**逐段按实测
   语速各做一次 WSOLA**（见下一章），段内仍无分块边界失真。CLI、旧版
   bundle、手工请求都走这个 sidecar，不能假设调用方都守规矩。
3. **退化尾音裁剪**：`trim_degenerate_tail()` 在变速前把 >1s 的尾部静音裁到
   0.25s（实测正常语义停顿最长 0.68s，不会误裁）；流式另有
   `is_silent_chunk()` + 连续 2 块静音提前 `break`，不把十几秒空白推给浏览器。
4. **临时默认关流式**：`speed != 1.0` 时服务端对每个 0.8s chunk 独立做
   WSOLA，状态不能跨块延续，实测边界样本跳变从 speed=1.0 的中位 0.1%/最大
   1.2% 涨到 2.8%/19.4%。当时先把默认切回只变速一次的整块链路；**这一条已在
   第二轮用跨 chunk 有状态 WSOLA 解决并恢复默认开**（见上文同名章节），
   此处保留是为了说明这一轮反馈的完整来龙去脉。

**修复后全链路复测**（同一批文本、同一个 sidecar、`speed=1.2`）：

| 字数 | 时长   | 折合语速   | 最长静音 | 时长比（实测/预期） |
| ---- | ------ | ---------- | -------- | ------------------- |
| 41   | 8.33s  | 4.92 字/秒 | 0.66s    | 1.00                |
| 48   | 10.08s | 4.76 字/秒 | 0.79s    | 1.03                |
| 55   | 11.34s | 4.85 字/秒 | 1.10s    | 1.01                |
| 96   | 19.68s | 4.88 字/秒 | 1.12s    | 1.01                |
| 164  | 33.37s | 4.92 字/秒 | 0.67s    | 1.00                |

流式 164 字也从 63 块 / 50.45s / 21.69s 静音变成 **44 块 / 33.60s / 0.67s
静音 / 4.88 字/秒**。换句话说：各长度语速收敛到 4.8~4.9 字/秒，长文本不再
丢字，静音回到正常句读量级。

边界用例：`scripts/voice/test_voice_preset.py` 的
`test_trim_degenerate_tail()` / `test_split_long_text()`，
以及 `packages/web/tests/voice-block.test.ts` 的 B6/B7。

## 逐块语速伺服：为什么「句子一长就不行了」（2026-11-06 第三轮）

### 反馈与业界调研

用户反馈「还是存在语速跳变，句子一长就不行了」。这一轮先做系统调研
（针对性检索 4 组 + 跨源综述），结论是长文本/流式 TTS 的「不连贯」不是
一个缺陷，而是**四类根因叠加**：

| 层面   | 根因                                       | 业界主流做法                                                                                           |
| ------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 文本侧 | 缺前瞻：看不到后文就无法决定重音与句末升降 | 语义感知分块（句末硬切、逗号软切）、首块激进后续保守、`marker_boundary` + 有限 lookahead               |
| 模型侧 | 每段从句首重新起势，语速/能量/基频各自重置 | CosyVoice 2 chunk-aware causal flow matching、CAM-TTS 上下文记忆、LiveSpeech 2 / StreamFlow 原生连续流 |
| 声学侧 | 段间没有状态传递                           | 声纹锚定 + 固定 seed/temperature、上一段音频尾部作 acoustic prompt                                     |
| 音频侧 | 相位不连续、机械 padding                   | 50~200ms 微停顿、crossfade、连续 PCM 帧                                                                |

几条对本仓最有用的判断：

- **按固定字数硬切是反模式**：「永远在句末切，宁可不整齐也别硬切」；块长没有通用最优值，中文生产系统常见 35~60 字，必须按具体模型实测。
- **模型按 chunk 自选语速、没有上一块的记忆**：inkwell 实测同一集里句子间语速能从 2.25 跳到 3.12 words/s；人类变化约 67%，模型可达 150%。
- **标准补救是「逐块实测字/秒 → 拉回全局固定基准」**：inkwell `pace-fix.mjs`（ffmpeg atempo）、ElevenLabs 字幕流水线（先按预测 `speed` 原生生成，再用 ffprobe 实测 + atempo 兜底，单次压缩上限 1.20×）。关键是目标必须取**全局固定值**，用本轮中位数会漏掉「整段一起快/一起慢」。
- **不切分才是终极解**，但需模型侧支持：Prosodic Boundary-Aware Streaming（arXiv:2603.06444，边界标记 + 滑窗 prompt + 上一段音频尾部锚，长文本 WER 71.0% → 4.8%）、LiveSpeech 2（Mamba 单流）、StreamFlow（分块注意力）。**CustomVoice 是预置 speaker，不支持 `ref_audio`**（只有 Base 模型支持 voice cloning），所以「上一段音频尾部作 prompt」这条低成本锚在当前模型上用不了。

### 本机实测：主因不是分段，是模型按块自选语速

控制变量实验把上一轮的结论推翻了一半。`/tmp/probe-segment-rate.py`：

| 样本                         | 字数 | 折合语速（speed=1.2）   |
| ---------------------------- | ---- | ----------------------- |
| UNIT 短句                    | 20   | **5.75 字/秒**          |
| UNIT 单块                    | 41   | 4.92                    |
| 164 字切成 4×41              | 164  | 4.92，段间极差 **0.0%** |
| 真实长句（无标点）切成 48+41 | 89   | **6.31 / 6.39 字/秒**   |

重复文本分段时段间完全一致，所以「分段」本身不是主因；**文本标点密度/结构一变，语速就跳约 29%**。
`/tmp/probe-rate-normalize.py` 直接量模型原生音频，6 种文本落在 **4.09~5.35 字/秒**
（极差 26.8%，max/min 约 31%）。

`/tmp/probe-maxtokens.py` 同时解释了为什么 48 字分段不能取消：41 字在 125 token
正常 EOS（10.00s）；96 字**完全不 EOS**，时长严格等于 `max_tokens/12.5`
（35.12 / 28.08 / 24.56 / 21.04s），且「有声结束」恒定 9.35s —— 模型只念了约
38 字，后面全是静音。收紧上限只能缩短静音，救不回被吞掉的字。

结论：前几轮修的都是**波形边界**（有状态 WSOLA）和**退化静音**（分段/裁尾），
而 `speed` 一直是「整个请求一次等比变速」——只能整体放大/缩小，**压不住块间
相对语速差**。这才是「句子一长就不行」的根。

### 落地方案

把「全局等比变速」换成「逐段语速伺服」：

```
目标语速 target = TTS_CHARS_PER_SECOND × speed        # 4.1 × 1.2 = 4.92 字/秒（全局固定）
每段：裁退化尾音 → 裁首尾机械静音 → 实测 actual = 等效发音单元 / 有效时长
      倍率 s = clamp(target / actual, 0.75, 1.65)
      对该段做一次 time_stretch_wsola(samples, s)      # 保调，只变速一次
拼接：段间插入 60ms 微静音，掩盖两次独立生成的相位跳变
```

- `trim_speech_edges()` 只裁句首约 88ms / 句尾约 46ms 的机械 padding，**句内语义停顿保留**（实测最长 0.68s）；否则短句会被误判成「读得快」。
- 目标取全局常量而不是本轮中位数；倍率钳在 0.75~1.65（上限见下文长文本专项第 6 条：纯拉丁复合词块实测需要 1.61 倍），超出的多半是退化段，硬拉只会毁音质。退化另由 `trim_degenerate_tail()` / `compress_internal_gaps()` 处理。
- 整块 `/tts` 用 `time_stretch_wsola()`，流式 `/tts/stream` 用 `StreamingWsola(s)` 分块喂 —— 两者逐样本相等（上一轮单测保证），所以两条路径产出一致。
- 流式改成**逐段流水线**：一段生成完立刻吐，再拿锁生成下一段。首块延迟只等于首段生成时间；若先把所有段攒齐再吐，164 字实测要等 7.67s。

单测 `scripts/voice/test_rate_normalize.py` 锁住裁剪边界、倍率公式、钳制与
「归一化后语速收敛」；离线 6 种文本按 0.919~1.203 校正后全部收敛到
4.93 字/秒（±0.2%），语速极差 26.8% → 0.3%。

### 真机复测（sidecar pid 87850 / speed=1.2）

| 指标               | 修复前                        | 修复后                                                  |
| ------------------ | ----------------------------- | ------------------------------------------------------- |
| 8 种文本语速       | 4.92~6.39 字/秒（极差约 29%） | **4.89~4.94（极差 1.0%）**                              |
| 流式 vs 整块时长差 | 8.399 vs 8.333s               | **0.00%（8.338 vs 8.338s）**                            |
| 长文本边界最大跳变 | 13.53%（41 字段接缝）         | **2.0%**                                                |
| 164 字流式首块     | 7.67s（全段攒齐才吐）         | **1.91s**（逐段流水线）                                 |
| 14~164 字退化回归  | 55 字起 3.28 字/秒、21s 静音  | 全部 4.89~4.93 字/秒、最长静音 ≤1.07s、时长比 1.00~1.01 |

### 取舍（诚实标注）

严格归一化在数学上必须**先量出这一段实际读了多久**，只拿到第一片时无法预知，
所以流式首字延迟从第二轮的 218ms 退到「首段生成完」。网关严格同参实测
（41 字单块、热态）：

| 路径                             | 首字节     | 全部到达 |
| -------------------------------- | ---------- | -------- |
| 网关整块 `/api/voice/tts`        | **1882ms** | 1882ms   |
| 网关流式 `/api/voice/tts/stream` | **2045ms** | 2062ms   |
| 直连整块 `/tts`                  | 1971ms     | 1971ms   |
| 直连流式 `/tts/stream`           | 2001ms     | 2018ms   |

也就是说**单块 ≤48 字时流式已不再比整块快**（首字延迟由「首块字数」决定，
两条路径都要等这段生成完）。实际播报链路里前端首块 `FIRST_BLOCK_CHARS=14`
（生成约 0.7~0.8s），后续段在前一段播放期间并行生成（RTF≈0.2），播放不会断。
流式仍保有价值的场景是**单次超长请求**：164 字整块要等 4 段全生成完（约 8s）
才返回，而流式逐段流水线 1.91s 就吐出第一段（修复前要把所有段攒齐，需 7.67s）。

这是用「单块流式首字延迟 +约 1.8s」换「所有块语速严格一致」。若哪天更看重
TTFA，可改「首片按全局 speed 预吐、其余段末补偿」的双阶段方案：整段平均语速
仍能严格达标，代价是每段开头 0.4~0.8s 有一次语速台阶——正是本轮要消除的听感，
所以没有直接采用。

### 更长期的路（需换模型或训练，本轮没做）

当前模型能力边界决定了分段不可避免：CustomVoice 不支持 `ref_audio`，
`generate_custom_voice()` 也没有原生 speed / duration 控制，Qwen3-TTS 流式版
又属于「文本/语音 token 交错」架构，长时交互会发生 long-form collapse。
换到有边界标记 + 滑窗 prompt、或 Mamba / 分块注意力的原生连续流模型，
才能从根上取消「切分-拼接」这一步；代价是重新下载或微调权重，中文音色
也要重新选。这一层属于架构决策，先记录不动手。

### ASR 为什么换成 Qwen3-ASR

用户反馈「语音转换准确率不高」。用同一批音频做闭环 A/B（8 句 TTS 合成，
干净 + SNR 8dB 加噪两路，字符级 CER）：

| 模型                     | 干净      | 加噪      |
| ------------------------ | --------- | --------- |
| `whisper-large-v3-turbo` | 6.88%     | 6.88%     |
| `Qwen3-ASR-0.6B`         | **3.72%** | **5.89%** |

差异集中在两处，都是用户会直接感知的：

- **专有名词/数字**：whisper 把「四零四」写成 404、「王工」→「王公」、
  「Qwen3」→「Q稳」；Qwen3-ASR 干净条件下全对
- **简繁**：whisper 中文模式会输出繁体（「三点」→「三點」），Qwen3-ASR 不会

共同短板是**英文专有名词**（「Tauri」→「Tory」）。这个用 Qwen3-ASR 的
`hotwords` 治：实测同一句音频，不带热词输出「Tori」，带上就正确。默认热词表
是 `DeepCodeX / Tauri / Qwen3 / MLX / MCP`，可用环境变量覆盖：

```bash
DEEPCODE_ASR_HOTWORDS="DeepCodeX,Tauri,Qwen3,MyProject" bash scripts/voice/start.sh
```

### Qwen3-ASR 的权重怎么来

`mlx_audio.stt.load` 吃本地目录。默认找 `~/.cache/qwen3-asr-mlx`，不存在就
回落 whisper（`/health` 的 `asr.backend` 会如实说明用的是哪个）。

**不要指望它自己去 HuggingFace 下载**：本机访问 `huggingface.co` 不通

ModelScope 取（实测 5.9~17MB/s，965MB 约 1 分钟）：

网上说「mlx-audio 支持 CosyVoice」指的是上游项目能力，不是这个移植版。

「御姐音」不是某个预置音色 id，而是一段**可编辑的声音描述**：

```
成熟女性，中低音区，语速平稳，略带气声，克制不撒娇，句尾下沉
（mature female, low-mid register, steady pace, slightly breathy, restrained）
```

VoiceDesign 会把这段描述当成声学指令。本机实测（同一句话只改描述）：

| 描述                | 中位基频 |
| ------------------- | -------- |
| 成熟女性，中低音区… | 156.9 Hz |
| 年轻女孩，高音区…   | 320.0 Hz |

差近一个八度，说明描述是真的在起作用。所以改这段文字比换音色 id 更接近你想要的，
这也是配置里 `voice` 是自由文本而非枚举的原因。

英文括号部分不是凑字数：这个模型的训练语料以英文描述为主，中英并列对
「低沉、克制」这类倾向的还原更稳。

## 音色为什么会「一会儿一个样」，怎么修

用户反馈「音色还是出现了跳脱，前后不一致」。这一条在原理上是 VoiceDesign 的
固有缺陷，不是参数没调好。

### 先确认不是随机性

固定 seed（按音色描述派生）+ 温度 0.35 之后，**同一句话**重复生成三次：

| 引擎        | 三次基频中位数           | 三次时长             |
| ----------- | ------------------------ | -------------------- |
| VoiceDesign | 294.5 / 294.5 / 294.5 Hz | 4.72 / 4.72 / 4.72 s |
| CustomVoice | 244.9 / 244.9 / 244.9 Hz | 5.92 / 5.92 / 5.92 s |

逐位相同，说明随机性已经压住了。**问题出在不同文本之间**：VoiceDesign 每次
调用都要"现场设计"一遍音色，换一段文本，自回归轨迹就变了，音色描述被重新
诠释——同一描述下四句不同文本的基频中位数实测 170.2~200.0 Hz。

### 业界怎么做

- **预置音色**（CustomVoice）：音色是训练好的 speaker embedding，不参与采样，
  跨句天生一致。业界评价是「最稳定、推理开销最低、一致性最好，长文本不易崩」
- **先设计后克隆**（Design → Clone）：用 VoiceDesign 生成一段参考音频，再让
  Base 模型以它为 `ref_audio` 做 ICL。能保留自定义音色且锁死声纹，代价是要多
  一个 Base 权重、每次生成都要编码参考音频
- **VoiceDesign**：适合角色试音，业界不建议用于长篇定稿

### 现在选的是哪条

`qwen3-customvoice`（1.7B）。选 1.7B 而不是 0.6B 的原因：0.6B 不支持 `instruct`，
1.7B 支持——音色锁死的同时还能调情绪。

9 个预置音色（`/health` 的 `tts.speakers` 会列出来）：

```
serena  vivian  uncle_fu  ryan  aiden  ono_anna  sohee  eric  dylan
```

切换方式（`~/.deepcode/soul/config.json`）：

```json
{ "voice": { "engine": "qwen3-customvoice", "voice": "vivian" } }
```

`voice` 填音色名时直接用它；填一段描述（旧配置的写法）会自动落到默认音色
`vivian`，并把原描述当 `instruct` 传进去——这样「语速正常、吐字清晰、利落」
这类风格要求还能保留一部分，但音色本身不再由描述决定。

### 一个诚实的边界

**没有做量化证明「听感一定更好」**。可用的度量都不够硬：基频中位数会被文本
语调污染（陈述句与疑问句本来就不同）；频谱包络的余弦相似度两者都在
0.96~0.98（VoiceDesign 0.9597 / CustomVoice 0.9648，方向一致但区分度低）；
最该用的声纹编码器（`extract_speaker_embedding`）在这两个 8bit 权重上取不到。

支撑结论的是原理与业界共识，不是听感对照实验。要保留自定义音色，得走
Design-then-Clone（需要再下一份 Base 权重，本轮未做）。

## 播报为什么会有句间空档

用户反馈「前一句后一句中间卡顿」。实测 TTS 的 RTF≈0.19（**合成比播放快 5 倍**：
一句 3.5s 的音频只要 0.5~0.9s 合成），所以瓶颈不在合成速度。

真因在播放队列的**预取时机**：`warmPrefetch()` 原先只在 `playOne` 末尾调用，
那一刻当前句已经播完，下一句的合成才刚开始。于是每两句之间固定空等一次完整
合成时间——听感就是「说完了，停一下，下一句才出来」。

修法是在 `playOne` **之前**就预取（`packages/web/web/src/voice/player.ts`），
让合成与播放并行。回归用例 P7 锁住事件顺序（第二句的合成必须早于第一句的
`ended`）；把预取挪回原位置时该用例会失败，可以确认它真的测到了这个行为。

**后续已补上的两层**（见 `voice/playout.ts` 与上文「流式生成」）：

1. 采样级无缝排程：音频搬进 `AudioContext`，一次解码成 `AudioBuffer`，用
   `start(when, offset, duration)` 排到上一句结束的采样点上；句首 88ms / 句尾
   47ms 的机械 padding 用 `findSpeechBounds` 裁掉，停顿改由标点决定而不是模型
   padding。`AudioContext` 不可用时降级回 `HTMLAudioElement`（有元素切换开销，
   但一定出声）。
2. sidecar 流式输出 + 客户端边收边排：不再 `list(chunks)` 全量收集。流式块走
   `continuous` 规则直接相接，首字延迟 1.92s → 0.39s。

## 鉴权

sidecar 是**整机一份**的资源，而 token 是**按引擎实例**生成的——桌面端一份
（`~/.deepcode/soul/config.json`），Web 模式每个用户各一份
（`~/.deepcode/web-uploads/.engine-home/<hash>/.deepcode/soul/config.json`）。

所以校验的是**白名单**：本机所有配置文件里的 `voice.token` 都接受。

- 任何配置存在 token → 要求 `Authorization: Bearer <token>`，命中其一即放行
- 一份 token 都没有 → 不校验（仅便于本机首次调试）
- 每次请求按配置文件 mtime 重扫：**改 token 或新增 Web 用户后不用重启 sidecar**

为什么必须这样：早先只认桌面那一份，结果是 Web 引擎每次合成都被挡——
`POST /api/voice/tts` 直接返回 502「token 不匹配」，而错误信息还建议"重启
sidecar"，照着做也没用（重启后仍然只认桌面那份）。一个服务两个入口，就不
能只认一个凭证。

`127.0.0.1` 不等于安全——同机任何进程都能 POST 到这里，所以这层校验不能省。
白名单只是"接受本机所有合法引擎"，并没有放宽到"接受任意请求"：伪造 token
与不带 token 一律 401。

## 插话（barge-in）：现在做到哪一步

「能不能打断助手」是陪伴类语音交互的硬指标。当前的实现是**半双工 + 插话**，
不是真全双工，区别如下。

### 已经有的

播报期间挂一路人声监测（`MicCapture.startMonitor`），连续 300ms 超过阈值就认为
用户开口，立刻做三件事：

1. `queue.stop()` 停播（同时叫醒卡在 `playOne` 的队列，见 `voice/player.ts`）
2. 置 `interruptedRef` —— 模型这一轮后续的流式内容不再送合成，否则刚打断的
   回复会被下一个增量重新念起来
3. 免按住模式下直接开录（`startTalk`）——用户正在说的那句会被收进去，说完停顿
   自动提交。按住说话模式下不自动开录（那种模式要求手一直按着，自动开录只会莫名）

播报期阈值是平时的 2 倍（`VAD_PLAYBACK_FACTOR`）：外放的声音会被麦克风拾回来，
不抬阈值就会「自己打断自己」。系统级 AEC/降噪由 `getUserMedia` 的
`echoCancellation/noiseSuppression` 提供。

### 延迟预算

业界的 P50 口径大致是：

| 环节             | 预算                                               |
| ---------------- | -------------------------------------------------- |
| VAD 判定用户开口 | 200ms（本项目取 300ms，偏保守，为压掉咳嗽/碰桌子） |
| 停播             | 50ms                                               |
| 取消 LLM 流      | 50ms                                               |
| **合计**         | **约 310~400ms**                                   |

超过 P50 350ms / P95 600ms，用户开始感觉到「它没听见我」。所以停播走的是
「立即 pause + 叫醒队列」，不做淡出动画。

### 还没做的（真全双工）

现在是「停 → 再听」，不是「边播边听、开口即抢占」。差值在这两处：

- **没有流式 ASR**。录音收尾后才整段识别。**2026-11-07 复核更正**：当前 venv
  的 `mlx-audio 0.6.4` 里，`mlx_audio/stt/streaming.py` 只是一个
  `StreamingSession` **Protocol**（`feed`/`step`/`close`），真实实现只覆盖
  `whisper`(AlignAtt) / `voxtral_realtime` / `nemotron_asr`；本服务用的
  Qwen3-ASR **没有流式实现**，也不支持 `--stream`。旧版 README 写「接进来
  就能压到百毫秒级」并不成立。真机实测 0.85s 中文 WAV、sidecar 直连热态
  整段识别只要 **58~86ms**，所以这段的瓶颈不是识别本身，而是固定 900ms
  静默窗（现已支持动态档位，见下）与 **1.77~1.89s 的 TTS 首音频**。
  P1 必须先做流式 ASR 选型 A/B，不要照这段旧描述直接接线。
- **打断判定只看音量**。真正的双工要区分「用户在应答」与「用户在咳嗽/对别人说话」，
  这需要语义判断（比如先出一版 provisional 文本，看它是不是一个完整意图）

这两件事都不改现成链路的结构，属于增量，但都需要真机调，所以没有在没实测的
情况下先写。

### 首片预吐：评估结论是**暂不落地**（2026-11-07）

目标是把 TTFA 从当前网关实测 **1770~1919ms** 压到 800ms 级。业界做法是
「双阶段预吐」：首片按预测倍率先吐，其余段生成完再按实测倍率补偿。

但 `iter_stream()` 当前的严格语速归一化依赖 `segment_stretch_speed()`：
它要量出**整段**实际读了多久，才能把语速拉回全局基准 `4.1 × speed`。
只在拿到第一片时，这个倍率在数学上不可预知。硬做预吐有三笔没有付清的代价：

1. **会重新引入语速跳变**。首片与后续块必然是两条 WSOLA 时间轴，首片倍率
   事后无法回收修正；用户此前明确反馈过的「前后两句语速不一样」正是这个
   症状。现有 8 轮真机基线 `rate_spread_pct = 0.77%` 会失效，而现有 11 项
   指标里**没有**「同一轮首片 vs 后续块语速偏差」这一项，必须先补判据。
2. **锁粒度冲突**。MLX 生成器不能跨请求交错，现有实现用 `with self._lock`
   包住整段生成、`yield` 在锁外。预吐要在生成循环里 `yield`，要么让客户端
   读取占住推理锁，要么把锁切碎到每个 chunk（并发风险）。
3. **字数分配没有可靠依据**。剩余段要按「首片时长 / 总时长」占比估算字数
   才能算 `seg_speed`，这个估算是近似，短句误差尤其大。

**开关契约（待实现，不是现状）**：`DCX_VOICE_FIRST_CHUNK_PREEMIT=1` 才启用，
默认 `0`；启用时与现有 `iter_stream` 并列一条实验路径，关闭时音频必须逐字节
不变。启用前必须先补「同轮首片语速偏差」指标，并由用户做**真机听感 A/B**
—— 代理脚本受桌面 WebView 独立 JWT secret 限制，听不了，不能靠 TTFA 数字
变绿就放行。

本轮只记录方案与代价，**没有改 sidecar 生产代码**。是否动它，取决于用户
真机试听当前 P0 版本后的判断。

## 自动化连贯性验收（2026-11-07 新增）

「语音连贯」靠听感无法回归：句间卡顿、语速跳变、音色跳脱、连聊十几轮后
突然静默，都是间歇性的。这里把验收拆成**互补的两层**，都不依赖人耳判断。

### 第一层：编排层单测（CI 可跑，零外部依赖）

`packages/web/tests/voice-continuity.test.ts`，随 `npm test` 一起跑：

| 用例 | 锁住的契约                                                                                                  |
| ---- | ----------------------------------------------------------------------------------------------------------- |
| C1   | 连续 20 轮 SSE 喂句（每 4 轮故意漏一次 `finishFeed`），每轮都出声；所有句子拼回去恰好等于原文，不丢字不重念 |
| C2   | 流式连续块按采样点首尾相接，相邻块缝隙 **0**、不裁句首                                                      |
| C3   | 流式块内的语义停顿完整保留（整句模式才裁首尾 padding 并补 60ms 尾音）                                       |
| C4   | 流式每块 `gap=0` 且带 `continuous` 标记，时间轴顺序等于 chunk 到达顺序                                      |

### 第二层：音频信号真机验收

```bash
# 离线内核单测（合成信号，不需要 MLX / 不需要服务）
npm run test:voice:unit

# 真机 8 轮：自动选网关 8799，失败回落直连 sidecar 8791
npm run test:voice:continuity

# 快速冒烟（4 轮）
npm run test:voice:continuity -- --quick

# 落盘产物，之后可在没有 MLX 的机器上离线复核同一份结论
npm run test:voice:continuity -- --out /tmp/dcx-voice-run
python3 scripts/voice/check_continuity.py --replay /tmp/dcx-voice-run

# 自定义文本集（每行一条）或自定义阈值
python3 scripts/voice/check_continuity.py --texts my.txt --thresholds my.json
```

实现分三个文件：`continuity.py`（纯 numpy 指标内核，不 import MLX）、
`check_continuity.py`（采集 / 重放 / 判定 / 报告）、`test_continuity.py`
（合成信号回归，验证指标能检出坏样本且不误报好样本）。阈值外置在
`continuity-thresholds.json`，改阈值不用改代码。

**退出码**：`0` 达标，`1` 有指标越界（逐项列出实测值 / 阈值），
`2` **环境不可用、本次没有实测**——sidecar/网关没起来或鉴权材料缺失时
绝不把「没跑成」伪装成通过。桌面引擎注入独立 JWT secret，本脚本不能用于
桌面 WebView，只测独立 Web 引擎或 sidecar。

每轮的整块 WAV、流式每个独立 WAV、`manifest.json`、`report.json` 都会落盘。
模型即使固定 seed 也可能有机器差异，留原始音频才能事后对证或人工拖进播放器听。
`--replay` 写的是 `report-replay.json`，**不覆盖**原 `report.json`：重放可能带
不同的 `--thresholds`，不能让一次复核把原始验收结论改写成别的判定。

### 六个维度与阈值依据

2026-11-07 真机基线：gateway 8799、`qwen3-customvoice` / `sinan` / `speed=1.2`、
8 轮（4 条基础文本各重复两遍）、热态、预热一次后再计时。

| 指标                                    | 真机实测        | 阈值        | 依据                                               |
| --------------------------------------- | --------------- | ----------- | -------------------------------------------------- |
| `rate_spread_pct` 跨轮语速极差          | 0.77%           | ≤ 6%        | 服务端逐块伺服目标 4.92 字/秒；实测 4.91~4.95      |
| `max_internal_gap_ms` 句内最长静音      | 660ms           | ≤ 900ms     | 正常语义停顿实测 620~660ms                         |
| `long_gaps_total` 超 800ms 静音段数     | 0               | ≤ 2         | 门槛避开正常停顿，专抓「讲了几句断了」             |
| `stream_batch_duration_delta_pct`       | 0.00%           | ≤ 3%        | 流式拼接与整块应等时长                             |
| `boundary_jump_ratio` 块边界跳变        | 1.23            | ≤ 3         | 局部 ±10ms 差分 P95 为基准；注入 click 时飙到 37.8 |
| `f0_spread_pct` / `centroid_spread_pct` | 18.28% / 20.11% | ≤ 25% / 35% | 不同文本 F0 本来就会变，阈值有意放宽               |
| `same_text_f0_drift_pct` / 质心         | 0.00% / 0.00%   | ≤ 8% / 12%  | **严格对照**：同文本重复两次，固定 seed 应完全一致 |
| `ttfa_growth_pct` 前后半 TTFA 增幅      | 1.04%           | ≤ 60%       | 前后半是同一串文本（见下）                         |
| `min_stream_chunks`                     | 5               | ≥ 2         | 1 块等于没流式                                     |

同文本重复两遍的语速、F0、质心、块数、时长差逐项完全一致，说明司南预设

- 固定 seed 在本机是确定性的，这套门禁可重复。

### 三个踩过的坑（写进测试，别再退回去）

1. **语速口径**：分母必须是「等效发音单元」（`speech_units(text)`），时长取
   **整段**而非只算有声样本——长句静音占比 8%→25% 会把 4.92 单元/秒虚高成
   6.59，制造假的语速跳变（首版误报 19.98%）。2026-11-07 又发现拿
   `len(text)` 当分母会在中英混排时把发音量少算一半，详见下一节。另给
   `chars_per_second_speech` 作参考，两者一起看能分辨「语速变了」还是「停顿变多了」。
2. **TTFA 混淆变量**：前半跑短句、后半跑长句时，首版测出 107% 假增长
   （其实是 18/25 字 vs 41/38 字）。采集时把基础文本集**重复两遍**，前后半
   完全同序列，增长才只反映「越聊越迟钝」。另报 `ttfa_per_char_spread_pct` 参考。
3. **边界 click 判据**：用全信号差分 P95 做基准会随整体波形能量在 0.06~2.27
   乱跳；改用拼接点 ±10ms 的**局部** P95，健康音频稳定在 0.63~1.23。并且必须
   取**最坏边界**而非中位数——5 块里 1 个 click 用户就能听出来，中位数会被
   其余正常边界稀释（离线单测实测 0.446 → 0.452，等于测不出来）。

### 诚实边界

- 这一层量的是**音频与编排的客观指标**，不等于桌面 WebView 里的真机听感；
  播报开关点击、句间台阶、音色满意度仍需你本人确认。
- F0 / 频谱质心只是音色的代理指标，不是说话人验证；跨模型/跨版本不具可比性。
- `--replay` 复核的是**已保存的那次音频**，不能证明服务当前状态。改了服务端
  代码后必须重新真机采集。
- 这一层把整条文本**一次** POST 给 sidecar，覆盖不到前端「按句切成 9~13 个
  独立请求」的真实长文本链路。那一层由下一节的 `longtext_probe.py` 负责。

## 长文本专项：语速口径、音色与碎片（2026-11-07 第四轮）

真机反馈「长文本还是会变语速，音色变了，讲话不自然不连贯」。门禁全绿但
真机仍有问题的原因是**覆盖错了链路**：`check_continuity.py` 一次请求整段，
而前端 `SentenceStream + SpeechQueue` 会把 300~400 字切成 9~13 个独立
HTTP 请求，每个请求都是一次全新的自回归生成。

### 复刻真实链路后量到的东西

`longtext_probe.py` 按前端规则切句、封块，逐块请求 `/tts/stream`，测每块的
等效单元语速、F0、质心、段内静音，并与「整段一次请求」对照：

| 语料            | 块数 | 旧版语速极差 | 旧版块间 F0 极差 | 异常块                                        |
| --------------- | ---- | ------------ | ---------------- | --------------------------------------------- |
| 纯中文 316 字   | 9    | 1.21%        | 20.57%           | —                                             |
| 中英混排 421 字 | 13   | **76.37%**   | **54.39%**       | 13 字→9.42 字/秒；3 字→F0 304Hz / 质心 4455Hz |

原生语速（关掉伺服实测）在等效单元口径下极差 77.68%，说明模型确实会按块
自选语速；但把分母换成字符数后，伺服又会把中英混排误判成「读得飞快」，
倍率撞到下限 0.75 仍然压不回目标——**错误口径本身在制造跳变**，而且段间
各不相同的 WSOLA 倍率会顺带改变音色。

### 六处修正

1. **`speech_units()`**：标点 0、汉字 1、拉丁串按 2.8 字母折 1、数字每位 0.9、
   全大写缩写逐字母。服务端伺服与验收脚本共用同一份实现，纯中文不受影响。
2. **段级伺服**：`segment_servo_speed()` 用等效单元算倍率，目标仍是全局固定
   `4.1 × speed`；只对 <6 单元的极端碎片加 0.8~1.25 护栏。**阈值不能定高**：
   中英混排 48 字符常只有 15~20 单元，定 20 会把正常块全判成碎片、禁用
   伺服，A/B 实测语速极差反而从 21% 涨到 63%。
3. **前端不产生碎片**：后续块目标吃到 48 字上限（少一次独立生成）、
   `MIN_BLOCK_UNITS=10`，低于阈值的尾块并入前一块；并进去会超上限时从
   前一块尾部「借」一段重划切分点，拼接仍逐字等于原文。首块 14 字豁免保 TTFA。
4. **段内异常长静音**：`compress_internal_gaps()` 只压 >0.9s 的空白到 0.45s，
   正常句读（实测最长 0.68s）原样保留。
5. **借字符改按等效发音单元算**（集成门禁最后一处失败）：旧版把
   `MIN_BLOCK_UNITS - speech_units(碎片)` 直接当「字符数」往前借。中英混排
   1 个字符常只值 0.36 单元，缺 3 单元只借 3 字符，借完仍是 7.07 单元的
   `和 anthropic-provider。`，照样单独发一次合成请求，把语速极差从 1.38%
   拉回 21.27%。现在服务端 `rebalance_tail()` 与前端 `rebalanceShortBlock()`
   枚举合法切分点，只取「左右两段都 ≥10 单元」的，并优先标点、其次空格 /
   中英交界，绝不把 `openai-provider` 拦腰切成 `opena` + `i-provider`。
   前端另有 `pendingShort`：前一块已被消费进时间轴时先攒着，流结束由
   `flush()` 结算，不为几字碎片单独起一次生成。
6. **伺服上限 1.35 → 1.65**：纯拉丁复合词块 `openai-provider 和
anthropic-provider。` 模型原生只有 3.06 单元/秒，拉回 4.92 需要 1.61 倍；
   旧上限把它钳成 4.14 单元/秒，成为整条中英混排里唯一的离群点（极差
   17.08%）。它块内最长静音仅 20ms，不是退化段——退化已由
   `trim_degenerate_tail()` / `compress_internal_gaps()` / 门禁的
   `long_gaps_total` 负责，不该靠倍率上限兜。

### 最终实测（sinan / speed=1.2 / 四条语料）

| 语料       | 块数 | 单元语速极差 | 块间 F0 极差 | 最长静音 | 异常长静音 | 最短非首块单元 |
| ---------- | ---- | ------------ | ------------ | -------- | ---------- | -------------- |
| 纯中文     | 9    | 0.79%        | 18.30%       | 700ms    | 0          | 16.0           |
| 中英混排   | 13   | **1.66%**    | 34.64%       | 700ms    | 0          | 12.1           |
| 无标点长句 | 5    | 0.61%        | 13.42%       | 700ms    | 0          | 24.0           |
| 数字密集   | 8    | 1.00%        | 23.59%       | 380ms    | 0          | 12.6           |

旧版中英混排 76.37% → 1.66%，块间 F0 极差 54.39% → 34.64%。
门禁 `longtext_probe.py --check` 在生产 8791（最终代码、sinan、speed=1.2）
四条语料 **PASS**。集成门禁曾两度失败，恰好对应上面第 5、6 条修正：
先是 7.07 单元碎片（21.27% / 最短 7.1 单元），修完碎片后剩下纯拉丁
复合词块被 1.35 上限钳住（17.08%），才把上限提到 1.65。

### 诚实边界

- **时间窗 F0 极差**（2 秒窗的中位基频起伏）在中英混排上仍约 53.84%，同一条
  文本整段一次请求是 34.51%。差额来自 13 次独立生成的起头语调，属于
  CustomVoice 固定 speaker 无法完全消除的韵律起伏；`generate_custom_voice()`
  不接受 `ref_audio`，做跨段音色克隆需要换 base 模型权重，本轮没做。
  （2026-11-07 第五轮把拼接从「按标点 20/80ms gap」改回流式 `continuous`
  硬拼接后，此值由 52.47% 复测为 53.84%；逐块门禁判据不受影响，4 条仍 PASS。）
- 首片预吐仍未落地（见前文评估）；`DCX_VOICE_RATE_SERVO=0` 可一键回到
  完全不做变速的模型原生音频，用于 A/B 或排查。
- 以上全部是**本机 sidecar 实测**，不等于桌面 WebView 里的真机听感。

## 混合内容 × 长度矩阵（2026-11-07 第五轮）

上一节只覆盖 4 条 300~400 字长文本，且门禁强制 `min_blocks>=3`。真实陪伴模式
里既有「嗯，我在。」也有中英混排、金额百分比、URL/JSON、无标点长串和 600 字
长答复。`mixed_matrix_probe.py` 补一层**控制变量**的矩阵实测：5 长度档
（极短/短/中/长/超长）× 5 内容类型（纯中文/中英混排/数字密集/符号代码/
无标点）= 25 格，每种类型用固定句子池按长度拼前缀，所以同类型不同长度只差
长度、同长度不同类型只差字符构成。

逐格复刻前端分块并逐块请求 `/tts/stream`，边读边计时拿**真 TTFA**；播报侧
按 `continuous` 排程硬拼接（块间 gap=0）。四类指标：流畅性（静音、块间机械
静音、边界跳变、逐字可逆、串行欠流）、速度（TTFA / RTF / 整段一次请求对照）、
语速（等效单元/秒的块间与跨语料极差）、音色（F0 / 质心 / 时间窗 / 重复 3 次
PCM 逐位一致）。单块语料没有块间极差，报告标 `N/A` 并改判「与 4.92 基准及
全局 F0 中位数的偏差」，**不拿 `spread()=0` 伪装通过**。流式块边界落在模型
padding 静音里，边界跳变恒为 0、无区分度，硬判据换成块间机械静音 ≤200ms。

### 真机结论（生产 8791、sinan、speed=1.2，25 格 / 179 块 / 796.88s 音频）

| 维度   | 结论                      | 关键实测                                                                    |
| ------ | ------------------------- | --------------------------------------------------------------------------- |
| 流畅性 | ✅ / ⏳ 符号类有静音堆积  | 异常长静音 0、最长内静音 760ms、块间机械静音 ≤106ms；RTF ≤0.40              |
| 速度   | ⏳ 未达标                 | TTFA P95 1877ms（阈值 1500），最差 `plain:xl` 2268ms                        |
| 语速   | ✅ 长度无关 / ❌ 内容相关 | 长度组间 4.72%、超长前后半同文本漂移 ≤3.29%；内容组间 22.12%、跨语料 25.52% |
| 音色   | ✅ 达标                   | 跨语料 F0 21.25%、长度组间 6.37%；重复 3 次 PCM 逐位一致、F0 极差 0%        |

门禁如实 **FAIL 15 项**，集中在 `code`（语速极差 53~72%、中位 3.88 u/s）、
`num`（长/超长 38%）、`mixed`（长/超长 15%）与无标点长块的 TTFA。**没有**
为了通过而放宽阈值、删语料或改口径；这是新增覆盖发现的历史边界，不是
`b58a9333` 的回归。

### 根因：文本前端缺 TNS，不是伺服参数

把 `code:m` 离群块音频送回 `/asr`：`POST https://127.0.0.1:` 音频 5.54s 却只
转出「Post HTTPs.」；`{asr, tts}` 被逐字母念成「S R T E S」；`3000ms` 念成
「三千米秒」；`stream` 含混成「STMA」。`speech_units()` 按「拉丁 2.8 字母折
1」折算，逐字母念法的发音量被系统性低估，伺服倍率撞 1.65 上限，输出仍偏长。
**提上限或改折算系数只让指标好看**，音频已经生成成这样。

加一组 `spoken` 语料（与 `code` 信息量相同、把 URL/JSON/路径写成口语中文）
做 A/B：语速极差从 53~72% 降到 **0.12~1.16%**，中位语速回到 4.93~4.94，
TTFA 从 645~739ms 降到 476~524ms，分块数 26→14。结论是方向有效，但**本轮
没有实施 TNS**：它需要产品决策（是否逐字念代码、默认开关），按红线保持
`flag 默认 off`，不擅自改生产链路。

## TNS 文本前端规范化（2026-11-07 第六轮，默认打开）

### 为什么必须做

第五轮 25 格矩阵如实报出 15 项违规，ASR 回听给出了决定性证据：

| 原文                      |  音频 | ASR 实际念出的  |
| ------------------------- | ----: | --------------- |
| `POST https://127.0.0.1:` | 5.54s | **Post HTTPs.** |
| `{asr, tts}`              | 6.66s | **S R T E S**   |
| `3000ms`                  |     — | **三千米秒**    |

这不是语速伺服或音色参数的问题：模型对 URL / JSON / 路径这类非口语文本
生成轨迹发散，`speech_units()` 按「拉丁串 2.8 字母折 1」折算的发音量被系统性
低估，倍率撞上限后仍偏长。提高上限只会让指标好看、损音质；**先把送进模型的
文本变成可朗读的中文**才是根子。人工口语化 A/B 已验证方向：语速极差
53~72% → 0.12~1.16%、TTFA 645~739ms → 476~524ms。

### 打开与回退

| 层       | 做法                                                                               |
| -------- | ---------------------------------------------------------------------------------- |
| 生产默认 | `start.sh` 显式 `export DCX_VOICE_TNS=1`；`/health.versions.tns` 回显 `tns-1.0`    |
| 一键回退 | `DCX_VOICE_TNS=0 bash scripts/voice/start.sh`（**需重启**，模块在进程启动时加载）  |
| 单次关闭 | 请求体 `{"tns": false}`，只影响本次，供 A/B 真机对照                               |
| 核对实现 | `POST /tts/normalize` 只回规范化结果、不加载模型，探针用它防「本地规则与线上分叉」 |

实现只有一份权威规则 `text_normalize.py`，在 `_handle_tts` / `_handle_tts_stream`
的 `apply_tns()` 里生效；**只改送去合成的文本，界面上展示的原文一个字不动**。
Web 网关重建请求体时不带 `tns`，因此桌面端沿用 sidecar 的环境变量默认值，
请求级开关仅直连 / 探针可用。

### 规则（按固定顺序，全部确定性）

| 顺序 | 规则                                      | 例子                                                                                                     |
| ---- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| ①    | URL / IP / 端口 / 路径                    | `https://127.0.0.1:8791/tts/stream` → `加密网址 一二七点零点零点一，端口八七九一，路径 语音合成，stream` |
| ①    | 嵌套 JSON、`:`、true/false/null           | `{ok: true, model: {asr, tts}}` → `ok 是 真，model 是 语音识别，语音合成`                                |
| ①    | 用户主目录 / 隐藏目录 / 扩展名            | `~/.deepcode/soul/config.json` → `用户主目录下的路径 隐藏目录 deepcode，soul，config 点 json`            |
| ②    | 单位 / 百分比 / 版本 / 日期 / 编号 / 电话 | `3000ms` → `三千毫秒`；`18.6%` → `百分之十八点六`；`v2.14.3` → `版本二点十四点三`                        |
| ③④   | 有限同义缩写白名单                        | `GET`→读取、`ASR`→语音识别、`npm`→Node 包管理器                                                          |
| ⑤    | 符号                                      | `=`→等于、`#10247`→编号一零二四七、`&&`→并且、`@`→艾特、`[voice]`→voice、`A/B`→A 和 B                    |

四条红线：

- **诚实降级**：没命中的原样返回，看不懂的结构不猜语义、不补内容；超大数字退化为逐位读。
- **幂等**：`normalize(normalize(x)) == normalize(x)`，前端若将来也做规范化不会串改。
- **不误伤口语**：纯中文、无标点长句、普通中英混排（`session.ts` / `openai-provider` /
  `X-Tts-Voice`）零改动；连字符复合词整体跳过缩写白名单。全大写缩写与纯缩写分开，
  避免把「你 get 到了吗」改成「你 读取 到了吗」。
- **口径一致**：语速分母改用 `speech_units(normalize(text))`。`longtext_probe.py`、
  `mixed_matrix_probe.py`、`check_continuity.py` 都加了 `--tns on/off`，
  off 逐字复现旧基线，on 才按真正念出来的文本算单元数。

### 验收

```bash
npm run test:voice:tns:unit   # 119 项离线检查：15 条 golden、数字读法、幂等、降级、覆盖率
npm run test:voice:tns        # 15 场景 × off/on 双跑 + 每路 ASR 回听 + WAV 落盘
npm run test:voice:longtext   # 四条长文本，默认 TNS on，仍 PASS 4/4
npm run test:voice:matrix     # 25 格矩阵，默认 TNS on；--tns off 可复现旧基线
```

`tns_probe.py` 不靠波形自证：每路音频都送回 `/asr`，看模型**实际念出了什么**，
按 fixtures 里的同义关键词组与荒谬模式判定。可听样本落在
`<out>/audio/<scene>-off.wav`、`-on.wav`、`ab-<scene>.wav`（off → 0.7s 静音 → on）。
规则输出固化在 `tns-fixtures.json`，Python 单测 / 服务端 `/tts/normalize` /
真机探针三方共用。

首轮 15 场景如实报出 2 项违规：ASR 把 `config` 写成 `Config`（大小写折叠即可，
不是 TTS 错读）、`npx tsc` 被逐字母念成「N P X T S C」拖出 23.01% 语速偏差。
后者按 ASR 证据把 `npm/npx/tsc` 加进白名单后回到 4.88 单元每秒，
**没有放宽任何阈值**。最终 15/15 场景、代码层 15/15 一致、门禁 0 项违规。
25 格矩阵 on/off 全量对照与逐场景 ASR 原文见
`docs/proposals/super-agent/voice/tns-acceptance-2026-11-07.md`。

### 诚实边界

- TNS 是**有限规则集**，不是通用文本理解：未知缩写、新类型非口语文本原样透传，
  遇到就要补白名单并重跑 ASR 回听。`DCX_VOICE_RATE_SERVO` 之类大写下划线标识符
  仍会被模型连读成含混串（真机 ASR：`DCXViewWithRadiusEverAll`），本轮没有猜语义。
- 规范化让「看到的字」与「听到的字」略有差异，这是 TNS 的固有代价；
  百分比、版本号、路径的中文读法由 golden fixtures 锁定，可逐条审计。
- ASR 自己会认错字（「首块」→「手快」、「session.ts」→「session TS」），
  关键词才用同义组；不应把 ASR 错字当成 TTS 错读。
- 网关路径没有做脚本级端到端验证（桌面 WebView 用独立 JWT，脚本不代跑）；
  sidecar 单点生效由 `/tts/normalize` 与直连真机覆盖，**桌面端真实听感仍需本人确认**。

## 结构感知分块（2026-11-07 第七轮，默认关）

TNS 打开后 25 格矩阵仍剩 7 项违规，其中唯一与 TNS 相关的是 `code:xl`
块间语速极差 **43.71%**。调研报告
`docs/proposals/super-agent/voice/tns-residual-fix-research-2026-11-07.md`
定位到根因**不在服务端**：服务端顺序本来就是
`apply_tns(整个请求文本) → split_long_text(规范化后文本)`，只要一个请求里
能看到完整的 `{...}` 就能还原结构。真正切碎 JSON 的是前端两处——
`sentence.ts` 的弱断句符含 `,` / `:`，`player.ts` 无标点时按 48 字硬切。

所以修法**不是再写一份 TS 版 TNS**（对照实验只降到 27.39%，还把 `voice`
切成 `v`/`oice`），而是给三处切点加「原子边界保护」：成对 `{} [] ()`、
ASCII URL、POSIX 路径、拉丁词、数字串。切点落在原子内部一律后移到边界；
实在没有合法切点时允许单个请求块到 59 字，交给服务端规范化后二次切分。

### 开关契约（三处独立，默认全关）

| 位置     | 开关                                                   | 默认 | 回退                                                       |
| -------- | ------------------------------------------------------ | ---- | ---------------------------------------------------------- |
| 前端     | `localStorage["dcx.voice.atomicChunk.v1"] = "1"`       | 关   | 删除键或置 `"0"`，下次开录生效                             |
| 服务端   | `DCX_VOICE_ATOMIC_CHUNK=1 bash scripts/voice/start.sh` | 关   | 去掉变量重启；`/health.versions.atomicChunk` 回显 `on/off` |
| 门禁探针 | `--atomic`（`longtext_probe` / `mixed_matrix_probe`）  | 关   | 去掉参数                                                   |

**关闭时前端切块、服务端分段与 `031f1cc2` 逐字一致**：450 条文本（含
TNS 规范化后）对比旧版 `split_long_text` 差异 0 处；`code:xl` 关闭态仍是
26 块 / 5 处切断原子。打开后 `code:xl` 变为 23 块 / 0 处切断原子，
逐字可逆、最短非首块 ≥10 单元。

三者的关系要说清：**前端偏好是必要条件**——只有它保证完整 JSON 进入同一个
请求，服务端 TNS 才有机会还原结构。真机 A/B 的 6.84% 是在
`DCX_VOICE_ATOMIC_CHUNK=0`（服务端默认关）下测得的；服务端那层只兜住
规范化后残留的拉丁词/数字串，是可选增强，不是收益来源，也没有单独 A/B。
门禁探针的 `--atomic` 只替换「前端复刻切分」，不碰服务端开关，正好对应
「前端打开 + 服务端默认关」这一主要生产态。

### 同源实现与跨语言一致性

`scripts/voice/atomic_chunks.py` 与 `packages/web/web/src/voice/atomic.ts`
是同一套原子判定；`scripts/voice/atomic-parity-fixtures.json` 由 Python 生成，
两侧单测读同一份数据比对 `atomicSpans` / `splitLongText` /
`rebalanceShortBlock`，防止「门禁测的复刻」与「真实前端」漂移。
`longtext_probe.frontend_blocks(text, atomic=...)` 是门禁唯一权威实现，
`chunking_ab_probe.py`、`mixed_matrix_probe.py` 都调用它。

### 诚实边界

- 这是**灰度开关，不是默认修好**：桌面 WebView 真机听感仍需本人确认。
  前端偏好是必要条件（保证完整 JSON 进同一个请求），服务端变量只是

  与矩阵语料（纯文本）链路不完全等价。
- 服务端那一层只兜住规范化后的残留拉丁词/数字串，仍严格守 ≤48 字。
  **2026-11-07 P1 补测修正了「不是必要条件」这句**：服务端 atomic 关闭时，
  前端 atomic 放出的 54~59 字请求会被 `split_long_text()` 二次切分，把
  `voice` 切成 `voic`+`e`；打开服务端变量后切在 `voice，` 后。见下一节。
- **⚠️ 全量 25 格矩阵实测（2026-11-07）**：单独打开 atomic 后 `code:xl`

  合成的 54 字超长块被服务端二次切分，短段句内静音把单元语速拖到
  3.396 u/s。语速类违规总数没降，只是换了格子，因此**不建议单独默认打开**。
  曾试过让两格都达标的替代策略，代价是 5.9 单元碎片、违反 ≥10 单元护栏，
  未采用也未放宽阈值。详见
  `docs/proposals/super-agent/voice/atomic-chunk-p0-2026-11-07.md` §5.3/§5.5。
  与 P1 / 服务端 atomic 叠加后的实测见下一节。
- 其余历史违规（`plain` 首块/全局 TTFA、大写下划线标识符、跨段 F0、
  网关 `tns` 不透传）**不在本轮修复范围**，见调研报告 §4/§7。

## 短块句内静音上限（2026-11-07 第八轮 P1，默认关）

`num:xs`（`首块 192 毫秒，整块 1821 毫秒。`，14.3 等效发音单元）在 TNS 打开后
仍有 **20.57%** 语速偏差。根因不是「读得慢」：有声语速 5.219 u/s 反而偏快，
是模型在短数字句里插了 4 段句内静音（最终输出合计 0.900s）。

**更关键的一层（上一轮没看到）**：短句被撑到原始约 6.0s，逐段语速伺服的倍率
被钳在 `TTS_RATE_SPEED_MAX=1.65`，数学上够不到 4.92 u/s 目标，所以伺服自己
修不了。把静音在**伺服之前**压短，倍率才落回可达区间——这是 P1 真正生效的
机制，也解释了 `code:m` 在 atomic 下的 3.396 u/s 为什么是同一类问题。

### 规则与开关契约

| 位置     | 开关                                                | 默认   | 作用                                            | 回退                                           |

## 稳定音色身份：为什么「门禁全绿，长文本还是一句一个样」（2026-11-08 第九轮）

真机反馈「长文本还是会变语速，音色也是不同句子不一样」。这一轮先复刻真实链路
量数据，结论是**前面几轮的门禁覆盖错了配置**，而生产配置本身有一个没被约束的
自由度。

### 覆盖盲区：门禁测的不是生产配置

`longtext_probe.py` / `mixed_matrix_probe.py` 一直硬编码 `voice=sinan,
speed=1.2`，而 `~/.deepcode/soul/config.json` 里实际是：

```json

  "speed": 1.35,

```

同一条 316 字语料、9 次独立请求，基线参数语速极差 **0.87%**，生产参数
**14.64%**。门禁四条全绿，真机照样跳——两者根本不是同一条曲线。

- **「把描述洗一洗」也救不了，反而更糟**：G 组手工删掉矛盾语速词后，
  `pure_cn` 第 6 块 39 单元只剩 3.57s / **10.9 单元每秒**（模型吞字），整体
  极差冲到 108.30%。说明任意改 `instruct` 都可能把某一块推出发散轨迹，

## 感知一致性：客观指标全绿后，人耳仍听得出块间差异（2026-11-08 第十轮）

第九轮后 `npm run test:voice:prod` 的单元语速极差已到 0.69%、同句重复合成
逐位相同，但真机听感仍觉得「不同句子音色不一样」。这一轮先找**真正可修的
量**，而不是继续调已经收敛的参数。

### 三组控制变量（8791、`--from-config`、TNS on）

| 实验                              | 结果                                                                                        | 结论                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 同一句连合成 5 次                 | 5 次 WAV `sha256` **完全相同**，`rms_voiced`/`peak` 方差 0                                  | 采样随机性已彻底锁死，排除                                             |
| 块间 F0 / 谱质心                  | 块间 22.19% / 39.59%；**单请求整段内部按时间窗** 41.03% / 62.84%                            | 这两个指标被元音、清辅音、声调、文本语调主导，不能当「音色漂移」直接修 |
| 同一波形只改 WSOLA 倍率 0.89~1.63 | F0 仅变 2.56%、响度 0.16dB，但 3-8k / 8-12k 频带掉 45% / 47%；与块间各指标相关性 \|r\|≤0.23 | 变速倍率只解释约三分之一的谱差异，不是主因                             |

**治本路径已证伪**：`mlx_audio` 的 `Qwen3TTSSpeakerEncoder` 只在
`tts_model_type == "base"` 时加载，当前 CustomVoice 权重没有它，底层
`ref_audio` / `ref_text` voice-clone + ICL 走不通（除非换 base 权重重做）。
每个请求只有本块文本、模型对每段独立预测韵律，**块间差异在模型层是必然的**。

于是把度量换到剔除音素影响的感知域：有声帧 RMS 与**长时平均谱（LTAS）**
四频带占比。基线（pure_cn 9 块）：响度极差 **3.77dB**、1-3k / 3-8k /
8-12k 频带占比极差 **174% / 173% / 135%**。

### 修复：段级感知一致性对齐

新模块 `perceptual_align.py`，在 `compress_segment_gaps()` 之后、语速伺服之前
对**整段**（不是流式 chunk）做一次确定性后处理；整块 `/tts` 与流式
`/tts/stream` 走同一位置、同一参数，逐样本等价性不变：

1. **阶段一 · 谱形**：把三个中高频带相对低频带的能量占比拉向按 speaker
   标定的参考画像，增益曲线经 250Hz 平滑、FFT 重叠相加应用，限幅 ±2.5dB；
2. **阶段二 · 响度**：谱形补偿后**重新测**有声帧 RMS，再单独归一到目标
   0.0398，限幅 ±3dB，并在峰值 >0.99 时收缩增益防削波。

> 两个实现坑都是真机 A/B 抓出来的，不是推断：① 谱增益与响度增益直接叠加
> 会过冲/欠冲（目标 0.0398 的块被压到 0.0305），必须分两阶段；
> ② 服务端画像测量原用 2048 点帧 / 0.02 阈值，而标定脚本用 40ms 帧 /
> 0.01 阈值，口径不一致导致「假收敛」（各块齐刷刷偏低 0.5~1.7dB）。现已统一
> 到 `continuity._windows()` 的口径。

**不改的东西**：不动音高（F0 22% 是文本语调，移调反而更像换人）、不改时长、
不改语速伺服、不改阈值文件。只对已标定的 `serena`（`sinan` 预设）生效，其它
音色**原样返回**，不猜一个目标去强行拉。

离线证伪（对**最终输出波形**直接跑对齐）显示 K 加权极差 `0.94/0.98 → 0.00dB`

### 落地修正：把对齐移到变速之后

两条合成路径（`iter_stream` / `synthesize`）同步改为
**伺服倍率 → `time_stretch_wsola()` 整段变速 → `align_segment()` → 按 interval 纯切片**。
`align_segment` 不改变样本数，所以伺服倍率先算后算完全一致；流式原本也是
攒齐整段才吐，改后 TTFA 只多几十毫秒纯 numpy 处理。`StreamingWsola` 生产
路径不再使用，类与单测保留作能力备份。

第十一轮两个增量（默认开、独立可回退）：

1. **K 加权感知响度**：ITU-R BS.1770-4 两级 biquad（high-shelf +4dB
   @1681.974Hz + 二阶 high-pass @38.135Hz Q=0.5），按 24kHz 实时算系数；
   响度归一目标由未加权 RMS 换成 K 加权有声帧 RMS，**只归一一次**。

   不是把自然句尾衰减压成零。

## 第十二轮：主观回归 —— 撤掉逐段 EQ 与边界增益，只做响度（2026-11-09）

### 用户反馈与定性

> 「长文本语速、音色还是不同句子不一样，**明显不一样，比前面优化表现还差**」

第十一轮客观指标是历史最好（K 加权响度极差 0.14/0.15dB），但**主观更差**。
这说明我们优化的目标函数错了：段间统计极差小 ≠ 听感一致。

### 根因：把「模型自然的段间差」换成了「后处理不均匀的段间差」

真机逐段处理量诊断（`/tmp/dcx_regress_diag.py`，生产态 22 块，直接调用服务端
对齐函数取每段实际施加的参数）：

| 处理项       | 实测逐段分布                                                                                                | 为什么听感更差                                                     |
| ------------ | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 频带增益曲线 | 同篇内既有 `[0,-2.5,-2.5,-2.5]`（压中高频）又有 `[0,+1.75,+1.46,-0.28]`（提中频），**频繁打满 ±2.5dB 限幅** | 等于给每句施加**不同的 EQ**，有的变闷有的变亮 → 「音色一句一个样」 |
| 响度补偿     | mixed_tech 三块以上**打满 ±3dB**（目标 0.04086 低于该语料实际中位数 0.04795）                               | 各段被压/推的程度参差不齐，且钳制后仍不达标                        |
| 边界增益     | 段间**正负交替打满 ±1.5dB**（块05 head −1.5、块06 +1.5）                                                    | 接缝处「这句起音被压、下句被推」，人工感                           |

LTAS 段间差本来就主要由**文本音素**决定（与第九轮 F0/谱质心同理），强行拉向
单点画像只会扭曲，不会统一。业界结论与第十/十一轮的「逐段孤立归一化」相反：
Xie 等综述指出逐段孤立优化会忽略跨段响度趋势、无法保证平滑过渡，推荐
「良好局部韵律 + **轻微全局归一**」；接缝应使用等功率 crossfade，而不是逐段
边界增益。

### 修复

1. **默认只做响度归一**（新 `align_loudness()`，profile `v12`）：不碰频谱、不碰
   边界、不改时长音高。输出在数学上等于「输入 × 标量」，单测残差 1.05e-07。
2. **响度目标改为 22 块真实输出的合并中位数**：K 加权 0.0456、未加权回退
   0.0417（旧硬编码 0.04086 偏离技术英文语料 17%，是打满限幅的主因）；
   限幅 ±3dB → **±2.0dB**。
   离线模拟过「请求内运行中位数 / EMA」方案，效果更差且破坏确定性，弃用。
3. **伺服上限 1.65 → 1.85**：官方门禁 mixed_tech 单元语速极差 **6.42% → 1.63%**。
   只影响触顶的拉丁复合词块（需求约 1.74），其余段倍率不变。

## 第十三轮：细致生成分析 —— 倍率自己就是音色变量（2026-11-11）

### 用户反馈与调研

「语速和音色还是存在前后不一致」。前几轮都在后处理归一化上打转（v10 段级
EQ → v11 K 加权+边界 → v12 撤掉只留纯标量响度），这次把重点放回**生成链路**：
到底是什么变量在逐段改变波形。

业界结论（2026-11-11 检索）：

- **NVIDIA MagpieTTS-LF（arXiv 2606.18485）/ NeMo Longform Inference**：长文本
  一致性的治本是**跨块 stateful inference**——把历史文本 token、encoder hidden
  state、attention focus 带进下一块，做篇章级韵律规划。论文明确把
  「naively concatenate independently synthesized chunks」列为有 prosodic drift
  的基线，Qwen3-TTS 正是其基线之一；边界能量台阶 SOTA 14.04dB，基线 17.91~30.62dB。
- **Faster Qwen3-TTS / SGLang-Omni**：`non_streaming_mode=True` 把完整目标文本
  放进 prefill 再解码可改善 prosody/consistency，且 TTFA/RTF 几乎不变；
  ICL 模式还指出 codec decoder 冷启动会「用错的声音重建」。
- **波形变速的硬边界**：工程实践建议 WSOLA 控制在 0.8~1.3×；>1.4× 会出现
  共振峰偏移、节奏与频谱包络无法解耦。模型侧时长控制（FastSpeech2 类）才无损。

**当前权重下改不了推理**：`mlx_audio` 的 `generate_custom_voice()` 不暴露
`non_streaming_mode`、历史 hidden state 或 `ref_audio`（CustomVoice 无
`speaker_encoder`）。所以只能从「逐段变量」里找可修的确定性失真。

### 真机诊断：两个根因，一个能修、一个只能诚实暴露

**因果实验（同一块波形只改 WSOLA 倍率）** —— 这是本轮最关键的一步，之前用
观测相关性得出「倍率只解释约 1/3 谱差异」是被文本音素差异淹没的假阴性：

| 倍率 | 谱质心  | 3–8k 占比 | K 响度  |
| ---- | ------- | --------- | ------- |
| 1.00 | 基准    | 基准      | 0       |
| 1.15 | −12.87% | −39.14%   | −0.26dB |
| 1.30 | −14.17% | −41.84%   | −0.29dB |
| 1.85 | −14.62% | −53.56%   | −0.76dB |

用**绝对频带能量**（不是归一化占比）对 10 块不同文本 × 7 个倍率标定，
跨文本标准差最大 **0.35dB** —— 证明这是**与文本内容无关的确定性 DSP 失真**。

**观测（生产切分 22 块，自由音色描述归一 sinan / speed=1.15）**：

| 项                                  | pure_cn                    | mixed_tech                 |
| ----------------------------------- | -------------------------- | -------------------------- |
| 伺服倍率范围                        | 0.86~1.29（1.50×）         | **0.76~1.54（2.03×）**     |
| 官方门禁「整块单元/秒」极差         | 0.87%                      | 1.69%（全绿）              |
| **人耳感知的「有声段单元/秒」极差** | **26.55%**                 | **29.91%**                 |
| 块内有声占比                        | 0.75~0.98                  | 0.74~0.99                  |
| 首块 vs 后续（质心 / 单元语速）     | 2004 / 1966Hz，4.73 / 4.73 | 2008 / 2070Hz，4.74 / 4.73 |

首块 14 字**不是**主因，排除。两个根因分别是：

1. **音色**：逐段伺服倍率跨度 2×，等于每块被施加不同强度的高频衰减。
2. **语速**：伺服按「整块时长（含句内停顿）」归一化，但各块停顿比例差 25%，
   人耳听到的吐字速度就差 30%。**门禁全绿但听感不一致**，与第九轮同类盲区。

### 修复：`wsola_compensation.py`

按倍率查标定表，用 FFT-OLA 把 WSOLA 削掉的高频补回去，位置在**变速之后、
响度对齐之前**（第十一轮的顺序教训）。补偿曲线**只由 seg_speed 决定**：

- 与 v10/v11 逐段 EQ 的本质区别：它们把每段 LTAS 拉向固定画像，增益由该段
  测到的谱决定、方向随文本变化，等于每句套不同 EQ；这里增益与文本无关，
  补偿的是已知 DSP 失真，**保留块间由文本造成的自然差异**。
- 单测 38 项锁住：同一倍率曲线逐元素相同、倍率=1 返回原对象、限幅 4dB、
  补偿后高频偏差 `0.85~3.07dB → 0.21~0.60dB`、时长/削波/确定性零回归。
- 默认强度 **0.6**（见下方取舍），`DCX_VOICE_WSOLA_COMPENSATION_STRENGTH` 可调。

### 强度扫描与取舍（不追求统计极差最小）

| --------------- | ------------------- | --------------------- |
| 0（不补偿）     | 44.62%              | 38.11%                |

| 0.9             | 35.36%（−9.26）     | 45.69%（+7.58）       |
| 1.0             | 34.24%（−10.39）    | 46.49%（+8.38）       |

仅 **0.02~0.10dB**），而是它的基线「高频~倍率」斜率本就接近 0

那正是 v11「客观全绿、主观变差」的老路；取保守 0.6 把退化控制在减半幅度，
最终判断交给主观听感（对比音频见下）。

### 语速口径：为什么不硬修

设某块有声时长 `V`、静音 `S`、等效单元 `u`。按整块口径归一化到 `target` 时，
有声段吐字速度 = `target × (1 + S/V)`，必然随停顿比例变化；反过来按有声段
口径归一化，整块速率又会随 `S/V` 变化（原生语速跨度 mixed_tech 达 68%）。
两者**数学上不可兼得**，除非把各块静音比例强行统一——那会给标点少的句子
凭空补停顿、给标点多的句子压掉自然换气，是又一次用后处理换统计指标。

所以本轮**不改伺服、不放宽阈值**，而是把盲区固化：`longtext_probe.py` 新增
`voiced_rate_units` / `voiced_rate_units_spread_pct`（只记录、不判定），
`--check` 输出强制并列打印两个口径。真机复测：
`pure_cn 0.70% vs 25.33%`、`mixed_tech 1.69% vs 30.41%`。

### 三条硬结论（都靠真机，不是推测）

1. **生成完全确定性，随机漂移与冷启动全部排除**。同文本连生成两次逐位相同
   （E1 噪声底 = 0）；同一段文本放在第 1 个请求 vs 前面跑 3 个无关请求后的
   第 5 个请求，指纹仍逐位相同（E2 = 0）。所以块间差异**只由文本/分块/后处理
   链路决定**，是可建模的，不是「模型每次随机挑了个嗓子」。
2. **「短块偏亮」不是确定性 DSP 失真，不能按长度做统一 EQ**。跨 4 个语料
   × 4 个前缀长度标定：14 字相对 44 字的谱质心偏移均值 +307.65Hz，但跨文本
   **σ=197.62Hz**；8–12k 频带偏移 +2.47dB、**σ=2.52dB**；F0 偏移 4.4Hz、
   σ=11.75Hz。对比第十三轮 WSOLA 标定（跨文本 σ 最大 0.35dB）——那里是
   确定性 DSP 失真可以补，这里 σ 与均值同量级甚至更大，是**文本内容主导**。
   按长度套 EQ 就是第十一轮 v11「客观全绿、主观翻车」的老路，明确放弃。
3. **用户描述与数据逐字吻合，最大两个跳变正是首尾短块**。pure_cn 分块
   `19,44,39,42,35,43,31,45,18` 字，相邻四频带距离
   `[8.597, 3.21, 3.911, 3.442, 5.196, 3.132, 1.565, 6.997]` dB——
   #1↔#2 最大、#8↔#9 第二，中间 31~45 字块两两只有 1.5~5.2dB。
   谱质心 #1 1011Hz vs #2 536Hz，F0 全段 204~253Hz。

### 模型侧：治本路径在本权重上不可用

已直接读 `mlx_audio/tts/models/qwen3_tts/qwen3_tts.py` 源码核实，不靠推测：

- `generate()` 在 `tts_model_type == "custom_voice"` 分支**直接路由到
  `generate_custom_voice()` 并丢弃 `ref_audio` / `ref_text`**；
- `generate_custom_voice()` 签名里**根本没有 `ref_audio` 参数**；
- `speaker_encoder` 仅在 `tts_model_type == "base"` 时构造，CustomVoice 为 `None`，
  即使传参考音频也不会提取 speaker embedding；
- `generate()` 的 ICL 分支（`_generate_icl`，带 `_icl_cache` 复用 ref_codes）
  只对 **base 模型 + `speech_tokenizer.has_encoder`** 开放；本机只有
  CustomVoice 与 VoiceDesign 权重，没有 Base 权重。

业界做法（Soniqo / NeMo Longform / Interspeech 2026 跨句状态论文）一致：
长文本音色一致靠**每段复用同一份 speaker embedding + prompt codec 参考音频**，
或跨块传递 encoder hidden state / attention prior；naive chunk 拼接是公认有
prosody drift 的基线。要真正治本，需换 `Qwen3-TTS-12Hz-*-Base` 权重、
准备一段固定参考音频与文本、把每块请求都改成 ICL 模式。这属于**换模型 +
改调用链**，会改变音色底子、需要下载权重（本机走 ModelScope），本轮未擅自执行。

## 第十六轮（2026-11-12）：修掉「整体音量大小会有起伏」

### 根因：v12 量错了「响度」

`loudness_drift_probe.py` 按 **ITU-R BS.1770 / EBU R128 integrated gated LUFS**

明显偏响，45–50s 分桶比 35–40s 高 **2.4dB** —— 与「40s 之后有起伏」吻合。

服务端 v12 的 `align_loudness()` 归一目标是「K 加权**有声帧 RMS 中位数**」。
关闭段级对齐、取 22 块真机原始波形做八种口径 A/B：

| ------------------------------------- | ---------------------------- |
| 不归一                                | 4.39 / 4.37 dB               |

| v12 **放宽到 ±6dB**                   | 3.35 / 1.65 dB（**更差**）   |
| integrated gated LUFS，±2dB           | 0.84 / 1.04 dB               |
| **integrated gated LUFS，±4dB**       | **0.00 / 0.00 dB**           |
| ungated LUFS / 全段 RMS，无限制       | 0.52 / 0.56 · 1.27 / 1.05 dB |

放宽限幅反而更差 ⇒ **不是力度不够，是量的东西不对**：帧中位数对段内静音

按 `sinan/1.3` 时代标定的，与 `serena/1.15` 也不匹配。

### 做法：v14 = 纯标量 + 正确口径

`align_loudness_lufs()` 输出恒等于 `x * g`（外加防削波时的整体收缩），
`g` 只由该段 integrated gated LUFS 决定：

- 目标 `LUFS_TARGETS["serena"] = -26.3 LUFS`，取两语料原始中位数
  −25.099 / −27.577 的折中（沿用第十二轮「避免过拟合单一文本」）；
- 限幅 ±4dB（真机最大只需 3.04dB，留余量），固定目标、不引入运行中位数
  / EMA（第十二轮已证伪，且会破坏「同请求同结果」）；
- 诚实降级：scipy 不可用、speaker 未标定、测量失败 → 退回 v12，绝不编造目标；
- **不改谱形、F0、时长、边界**，所以第十五轮被认可的音色一致性结构上
  不会被破坏。逐块指纹实证 raw vs 归一后谱质心 ≤0.5Hz、MFCC ≤0.046
  （PCM16 二次量化量级）。

`ALIGN_PROFILES = ("v11", "v12", "v14")`，默认 **v14**；请求级
`{"alignProfile": "v12"}` 或环境变量 `DCX_VOICE_ALIGN_PROFILE=v12 bash scripts/voice/start.sh`
一键回退。`/health` 回显 `alignProfile` / `lufsTarget` / `lufsMaxDb`。

## 第十七轮（2026-11-12）：修掉 v14 之后仍「时大时小」与「语速些许变化」

即第十六轮把**块间整体音量**修好了，但还有两层没修到。

### 根因一：integrated LUFS 是「整块一个数」，量不到块内与接缝

用 `loudness_drift_probe.py` 对用户指定的那条音频与真机 22 块重测，新增
「5s 桶有声中位数」「块边界 ±0.5s 电平跳变」两个口径：

| 口径（mixed_tech / pure_cn） | v12 改前 | v14 | 结论 |
| --- | --- | --- | --- |
| 块间 integrated LUFS 极差 | 3.34 / 1.90 dB | **0.00 / 0.00 dB** | v14 已修 |
| 5s 桶有声中位数极差 | 2.93 / 3.39 dB | 1.86 / **4.34 dB** | 跨块低频漂移仍在，纯中文反而更差 |
| 块边界 ±0.5s 跳变均值 | 2.50 / 3.74 dB | 2.33 / 3.62 dB | v14 几乎没碰 |
| 同上最大值 | 5.46 / 5.42 dB | 5.61 / 5.72 dB | 甚至略差 |

具体听感对应：用户那条 v14 音频 45–50s 为 −26.23 LUFS、50–55s 掉到
−28.09 LUFS；第 25–30s 是 −27.92 LUFS。这正是「时大时小」的位置。

**九种纯标量归一口径全扫描**（integrated gated / ungated、momentary
median / p25 / p75 / mean、两种 hybrid）：接缝跳变始终 2.3~3.8dB、5s 桶
极差始终 1.8~5.2dB —— **块级乘常数已到天花板**，`momentary_median`
虽能把块间有声中位数压到 0.00dB，却把 integrated 极差放回 1.80/1.03dB，
且 5s 桶与接缝一点没改善。残留来自块内，不是块间。

### 根因二：门禁语速口径与人耳口径差 20 倍

生产态真机门禁：整块单元/秒极差 **0.34% / 1.19%**（阈值 8%，PASS），
但人耳听的**有声段吐字速度**极差是 **16.56% / 20.94%**。WSOLA 等比例
拉伸有声段与停顿，`v_i / r_i = d_i / s_i` 恒定，改倍率消不掉这个比值；
两者只能折中，除非改句内停顿比例（那会伤自然度，不做）。

### 业界调研结论（本轮检索）

- EBU R128 / Tech 3342：**integrated（整段一个 gated 数）≠ short-term
  （3s 滑窗，人耳说的「某段更响」）≠ LRA（10/95 分位动态范围）**。
  长篇语音 LRA 典型 5~9 LU，广播只建议 <20 LU 并**不设硬目标**。
- 长文本 TTS 拼接实践：**per-segment normalization 会 flatten 自然动态、
  让 quiet lines shout**；应按整章/整个 voice 测一次，或只平滑
  「非语言动机」的边界跳变，而不是逐段硬拉平。
- WSOLA 后处理变速建议 0.8~1.3×，超 1.4× 清晰度下降；模型内时长控制
  才是无损路径（当前 CustomVoice 权重不支持，属治本未做）。
- 一致做法是组合策略：稳定 synthesis profile + 语义分块 + 感知响度归一
  + 边界处理 + 客观/主观双评估。

### 方案：v17 = 两块独立、可回退的改进

**A. 块内 3s 慢变响度整形**（`slow_leveling.py`，默认开，强度 0.7）

`v14 纯标量归一 → 慢变整形 → 再做一次 v14 纯标量归一`。整形按 K 加权
400ms/100ms momentary 曲线取 3s 滑动平均，把慢变包络相对本块有声中位数
的偏移按强度取反，生成**能量加权零均值**的 dB 增益曲线，插值到样本级。
零均值使各块增益基线都是 0，不需要跨块状态，流式/非流式确定且一致；
3s 窗只压 0.3Hz 以下漂移，100~400ms 的重音、句末减弱、自然停顿原样保留；
限幅 ±2.5dB，实测增益斜率约 5~7dB/s（1s 窗方案是 16~19dB/s，有 pumping 风险，未采用）。
二次归一让第十六轮的「块间 0.00dB」完全保留。

**B. 双口径语速折中伺服**（默认 `alpha=0.3`）

`k_new = k_old × ((s_i/d_i) / 0.90)^0.3`，`s_i/d_i` 是块内有声占比，
VAD 复用 `continuity` 的 40ms/20ms 帧与相对峰值门（与门禁同一口径）。
固定参考值 0.90，不用运行中位数，保证确定性。`alpha=0` 逐字回到第十六轮。

| 请求级字段 | 作用 | 环境变量 |
| --- | --- | --- |
| `slowLeveling` | 关掉慢变整形 | `DCX_VOICE_SLOW_LEVELING=0` |
| `slowLevelingStrength` | 强度 0~1（默认 0.7） | `DCX_VOICE_SLOW_LEVELING_STRENGTH` |
| `dualRateAlpha` | 语速折中 0~1（默认 0.3，0 回退） | `DCX_VOICE_DUAL_RATE_ALPHA` |

一键精确复现第十六轮（请求级，不必重启）：
`{"alignProfile":"v14","slowLeveling":false,"dualRateAlpha":0}`；
进程级回退：`DCX_VOICE_SLOW_LEVELING=0 DCX_VOICE_DUAL_RATE_ALPHA=0 bash scripts/voice/start.sh`。
`/health` 回显 `slowLeveling` / `slowLevelingStrength` / `slowLevelingSmoothS` /
`slowLevelingMaxDb` / `dualRateAlpha` / `voicedRatioRef`。

### 诚实边界

- **无 MOS / 双盲听测**，不宣称主观一定更稳；上面全是客观量，最终以试听为准。
- 慢变整形不再是纯标量：短时 400ms p95 跳变在 pure_cn 上从 4.42 升到
  **5.28dB**（+0.86dB），mixed_tech 不变。这是本方案已知的代价，换来了
  5s 桶极差 4.34→1.59dB 与接缝 3.62→2.54dB。若试听觉得句内不自然，
  把 `slowLeveling` 关掉即可回到第十六轮。
- `alpha=0.3` 让整块口径门禁余量变小：全量 4 语料里 `numbers` 已达 7.22%
  （阈值 8%），**换语料、换音色、换语速需重跑门禁**；可用
  `dualRateAlpha=0.2`（更保守）或 `0`（回退）。参考值 0.90 与 LUFS 目标
  −26.3 都只对 `serena/1.15` 标定。
- 音色「各句变化有一点」本轮**未动**：第十四/十五轮已证明它主要由文本与
  上游 `instruct` 主导，逐段 EQ 会把它弄得更差（第十一轮已证伪）。
- 治本路径仍是模型侧：Base 权重 + `ref_audio` / ICL / 跨块声学锚定 /
  模型内时长控制；当前 CustomVoice 权重不支持，后处理只能逼近。

## 已知限制（诚实边界）

写在这里而不是藏在代码注释里，因为每一条都会影响你的实际体验：

1. **`/health` 的 `ready:true` 只代表库可导入**，不代表权重已下载。首次合成仍要等 10~30s。
2. **鉴权只认本机配置文件里的 token**。sidecar 按 mtime 指纹热重扫，改 token
   或新增 Web 用户都不用重启；但如果 token 是从别处手填进请求的，会一直 401。
3. **ASR 只接受 16-bit PCM WAV**。前端已在浏览器侧用 `decodeAudioData` + `encodeWav` 转好，
   所以这条只影响你自己用 curl 调的场景。
4. **识别语言固定中文**（Qwen3-ASR 传 `Chinese`，whisper 传 `zh`）。中英混说时英文词
   更脆弱（实测「Tauri」→「Tory」），靠 `hotwords` 缓解，不靠放开语言自动判定。
5. **重采样是线性插值**，不是带抗混叠滤波的高质量重采样。对语音识别影响很小，
   但不适合当音频处理工具用。
6. **自由音色描述默认归一到稳定预设 `sinan`**（2026-11-08 第九轮）。`instruct`
   每次生成都与当前文本联合解释，中英混杂、含矛盾语速词的长描述实测会让
   长文本逐块漂移（纯中文语速极差 14.64%、中英混排 60.94%、接缝跳变 0.65）。
   要自定义音色请填 9 个预置 speaker 名或 `sinan` / `sinan-bright` 预设；
   `DCX_VOICE_STABLE_IDENTITY=0` 可恢复「整段描述当 instruct」，但会带回漂移。
   自定义描述的理解程度取决于模型的 instruct 能力，不是确定性控制。
7. **并发被串行化**。MLX 推理不是线程安全的，所以加了锁：两个人同时说话会排队，
   排队期间第二个请求表现为「慢」而不是「错」。
8. **Qwen3-TTS 没有原生 `speed`，变速在波形上做**。现在是 WSOLA 保调变速
   （`time_stretch_wsola`），纯正弦倍率误差 <1% 且 F0 不变；早先的 `np.interp`
   重采样会让音高跟着速度升（speed=1.25 时 +17%，像磁带快进），已弃用。
   真实语音上 F0 估计波动约 4%。Kokoro 走原生 `speed`，不受影响。
9. **首次加载占内存约 3~4GB**（ASR 约 1GB + CustomVoice 约 2.9GB）。
   本机 128GB 统一内存足够；8GB 机型不建议同时开两个引擎。
10. **首次加载约 13s**（权重已缓存），首次下载 1.8GB 视网络而定（本机实测 14.5 分钟）。
11. **流式变速按「段」有状态**：第三轮语速伺服之后，每个 48 字段有自己的
    WSOLA 实例与倍率（由该段实测语速决定）；段内分块喂 == 整段一次变速，
    逐样本相等，`speed != 1.0` 不再造成逐块重启失真。剩余物理边界：① 每块
    独立封装 PCM16 WAV，浏览器解码拼接有量化级微小跳变（speed=1.0 也存在，
    实测中位 0.1%/最大 1.2%）；② 段接缝是两次独立模型生成，现用 60ms 微静音
    掩盖，真机长文本最大跳变从 13.53% 降到 **2.0%**。整块 `/tts` 与流式音频
    逐样本一致（时长差 0.00%）。
12. **单次生成硬上限 48 字**：超过就在服务端自动分段（长文本会一路生成到
    `max_tokens` 上限且中途停止念字，见上文）。`trim_speech_edges()` 已裁掉
    句首约 88ms / 句尾约 46ms 的机械 padding，段间改插 60ms 统一微静音；
    但分段仍是两次独立韵律规划，停顿的「语义合理性」不如真人，只是不再有
    长空白或语速跳变。前端已把块长压到 48，正常播报不触发服务端分段。
13. **流式首字延迟不再是优势**：逐段语速伺服必须等该段生成完才能测速，41 字
    单块实测网关流式 **2045ms** vs 整块 **1882ms**，基本持平（第二轮曾做到
    218ms）。流式的剩余价值在单次超长请求的逐段流水线：164 字 1.91s 吐出
    第一段，整块要等约 8s。详见「逐块语速伺服」的取舍章节；若业务更看重
    首字延迟，需改双阶段预吐或换模型原生连续流。
14. **段级感知对齐（第十轮）不是音色克隆**：它只把响度与谱包络拉向一份按
    `serena` 标定的参考画像，F0 的自然语调起伏（块间 21~23%）原样保留。
    对齐后 `longtext_probe` 的 `boundary_jump_max` 在 pure_cn 实测 0.05
    （第九轮 0.003，对齐改变了段间幅度关系，仍远低于波形可闻阈值），
    mixed_tech 0.10；这两项不在 `--check` 判定项内，但报告如实落盘。
    要真正跨句锁定音色，需要换支持 `ref_audio` 的 base 权重并改调用链。
15. **门禁「单元语速极差」不是人耳语速**（第十三轮）：门禁用整块时长（含句内
    停顿）作分母，伺服按它归一化后全绿（0.70/1.69%），但块内有声占比
    0.74~0.99，人耳感知的有声段吐字速度极差实测 **25.33/30.41%**。两口径数学上
    不可兼得，详见第十三轮章节；探针已并列打印，判断时不要只看门禁数字。
16. **WSOLA 谱补偿不是音色克隆**：它只撤销变速本身的确定性高频衰减，不改变
    跨块生成状态、不修接缝、不修 F0。mixed_tech 的谱质心块间极差在补偿后
    **上升 5.19%**（38.11→43.30%），属如实记录的观察项；没有 MOS 数据前不宣称
    主观一定更好，请用 `/tmp/dcx-v12-v13/` 对比音频确认，或一键回退。
17. **「第一、第二音色不一样」目前没有后处理解**（第十四轮）：生成逐位确定性，
    差异来自每次分块都是独立自回归生成；当前 CustomVoice 权重不支持
    `ref_audio` / ICL 跨块锚定，本机也没有 Base 权重。逐段 EQ 已两次证明
    主观更差（v11），按长度做 EQ 被跨文本标定证伪（σ≈197Hz），稳态分块
    A/B 双向、默认关。**唯一治本是换 Base 权重 + 每段复用同一参考音频**，
    属于换模型，需先确认音色与权重下载可接受。
18. **稳态分块是默认关的灰度项**：`dcx.voice.steadyBlocks.v1` 写 `"1"` 才生效。
    纯中文 #1↔#2 距离改善 51% 但 #2↔#3 退化、频带均值整体变差，
    「全块下限」变体更是让 mixed_tech 门禁 FAIL。所以不宣称它「解决」了
    音色一致性；请先用 `/tmp/dcx-v14-ab/` 对比音频按自己的耳朵判断，
    再决定是否开启。
19. **WSOLA 补偿强度没有全局最优值**（第十四轮 B）：真机 5 档扫描显示纯中文
    越高越好、中英混排越低越好，交叉点在 `0.6` 附近但两边都不是最优。
    mixed_tech 的 17dB 级跳变来自英文专名块引起的模型音色切换，补偿强度
    0→1 只降 0.6dB。当前默认 `0.6` 是**折中而非最优解**；按主要收听内容
    用 `wsolaCompensationStrength` 自行调整，别期待它有治本效果。
20. **风格指令 `instruct` 会让模型逐块重新解释音色**（第十五轮）：这是
    「第一、第二明显不一样」的上游成因，DSP 补偿修不掉。零 instruct 能把
    1↔2 频带距离降 34%，但 **mixed_tech 官方门禁 FAIL**（异常长静音、
    响度 4.30dB、F0 28.89%）。改成预置名 `serena` 后门禁全绿、1↔2 频带
    两语料降 53.7% / 42.8%，代价是 F0 极差升到 33.25%、响度 2.45dB、
    音色少了「成熟/克制/句尾下沉」的调制。第十五轮未改生产配置，
    第十六轮经用户试听确认后才把 `voice.voice` 落到 `serena`（见上）；
    换 Base 权重做跨块声学锚定仍是唯一治本路径。
21. **v14 只压平段级整体响度，不压平句内动态**（第十六轮）：短时 400ms
    响度 p95 相邻跳变仍是 4.42~4.67dB，那是自然语调与停顿，动它就要上
    压缩器（第十二轮已证伪）。块间 integrated LUFS 极差虽到 0.00dB，
    LUFS 仍是 K 加权能量口径，不等于每个人对「音色亮度」的主观感受；
    没有 MOS 数据，不宣称主观一定更稳。目标 −26.3 LUFS 按 `serena/1.15`
    两条语料 22 块标定，换音色 / 换语速后未标定 speaker 会诚实降级到
    v12，需重新标定 `LUFS_TARGETS` 而不是直接套用。**第十七轮补记**：
    这里说的「句内动态」指 100~400ms 级语调，仍刻意不碰；v17 处理的是
    更慢的 3s 级漂移与块边界台阶，两者不是同一层，见第十七轮章节。
22. **双口径语速折中是有代价的取舍**（第十七轮）：`alpha=0.3` 把人耳的
    有声段吐字速度极差从 16.56/20.94% 压到 11.88/15.36%，代价是官方
    门禁的整块口径从 0.34/1.19% 升到 5.52/6.06%。全量 4 语料里
    `numbers` 已达 7.22%，距 8% 阈值只剩 0.78pp；**换语料 / 换音色 /
    换语速必须重跑 `npm run test:voice:gate:all`**，必要时用
    `{"dualRateAlpha": 0.2}` 或 `0` 回退。两个口径数学上不可兼得，
    不宣称「语速已完全一致」。
23. **慢变整形不是纯标量**（第十七轮）：整块 LTAS / 谱质心的统计权重会变，
    pure_cn 短时 400ms p95 跳变从 4.42 升到 5.28dB。虽然 `timbre_probe`
    统一尺子下的块间音色联合距离反而略降，仍以真人试听为准；
    `{"slowLeveling": false}` 精确回到第十六轮。
